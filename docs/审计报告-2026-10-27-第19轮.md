## 2. 本轮做了什么（安全视角）

### 2.1 补上 R1：内核自己验校验和

**第 18 轮的风险**：M2a 只校验魔数与版本。若 ADS 里的 `file_id` 被改而魔数保持不变，M2b 会用错误的 tweak 解密 → 得到乱码 → 应用若把乱码回写 → **文件损坏且不可逆**。

**本轮修复**：内核用 BCrypt 算 `SHA-256(bytes[0..24])`，与前 8 字节校验和比对，不匹配则**绝不采信**其中的 `file_id`。

```text
魔数/版本不对      → AdsBroken    （不是我们的标记，或格式坏了）
魔数对但校验和不符  → AdsTampered  （是我们的标记，但内容被改过 —— 安全事件）
全部通过           → AdsHit       （可用于 M2b 加解密）
```

`AdsTampered` 单独计数的意义：运维能区分"这里有别的程序的 ADS"和"有人在改我们的标记"，后者是要按安全事件上报的。

### 2.2 算法一致性：两端交叉验证（关键）

内核用 BCrypt、用户态用 Rust `sha2`。**两者若不一致，所有合法标记都会被判成篡改，M2b 直接瘫痪。**

交叉验证（本机实测）：

| 实现 | 校验和（前 8 字节） |
|---|---|
| Rust `sha2`（`core/src/meta.rs`） | `6463c5099f757a10` |
| **CNG / BCrypt**（.NET `SHA256` 走的就是它） | `6463c5099f757a10` |

**完全一致。** 并把这个 32 字节样本**锁死**为黄金样本测试（`golden_meta_bytes`），任何人改哈希算法或字段偏移都会立刻失败。

### 2.3 安全默认：BCrypt 打不开就拒绝加载

`DriverEntry` 里 `BCryptOpenAlgorithmProvider(BCRYPT_SHA256_ALGORITHM)` 失败 → **直接返回错误，驱动不加载**。

理由：验不了校验和就守不住 R1，带着这个缺陷运行等于给数据损坏留口子。宁可整个驱动起不来（可诊断），也不要静默降级（会毁数据）。

## 3. 安全问题

### 3.1 A1（**中危，遗留，未解决**）裸 SHA-256 挡不住"知道算法且有写权限"的篡改

**问题**
校验和用的是**无密钥**的 SHA-256。攻击者若能写 ADS，就能改 `file_id` 并**重算校验和**，从而绕过校验。

**后果评估（重要，别夸大也别缩小）**
- 攻击者**无法借此窃取数据**：他改的 `file_id` 会导致解密出乱码，而密钥不在他手里；
- 真实后果是**数据不可读**（等价于破坏性攻击）；
- 所以这条不是"机密性失守"，而是"可用性/完整性风险"。

**为什么本轮不做 HMAC**
改用 `HMAC-SHA256(设备密钥, ...)` 确实能防伪造，但引入一个**更严重的可靠性风险**：设备密钥一旦丢失，**所有文件的标记都无法验证** → 全部文件不可解密。对"驱动坏了还能救"的产品定位来说，这把钥匙太关键，不能轻率引入。

**计划缓解（成本从低到高）**
1. **侧表 `Data/DriverIndex.db`**（原 M2 计划项）：路径 → file_id 独立记录一份，ADS 被改坏时能对照恢复。**这是首选**，不引入新密钥；
2. 服务端签发不可猜测的 `file_id`（而不是本地随机），配合审计日志可追溯"谁在什么时候改了标记"；
3. 若将来确需防伪造，再加 HMAC，并把设备密钥纳入密钥托管（与 PolicyKey 同一条链路）。

### 3.2 A2（低，遗留）每次探测一次 `BCryptCreateHash` / `BCryptDestroyHash`

有内存分配开销（估计 1~3 μs/次）。48 字节的哈希本身 <1 μs，开销主要在句柄创建。

**计划**：并入第 18 轮的 R3（stream handle 上下文缓存）——同一文件只探测一次后，这个开销自然摊薄。若届时不满意，再考虑 `BCRYPT_HASH_REUSABLE_FLAG` 或线程局部 hash 对象。

### 3.3 已核查、确认无问题的项

| # | 检查项 | 结论 |
|---|---|---|
| 1 | **内核链接库选择** | 内核**不能**用 Windows SDK 的 `um\bcrypt.lib`（那是用户态导入库），必须用 WDK `km\ksecdd.lib`（内核安全支持提供程序）。第一次链接 `bcrypt.lib` 直接 `LNK1181`，已修正 |
| 2 | **IRQL** | `BCryptCreateHash/HashData/FinishHash` 都要求 `PASSIVE_LEVEL`；`OugMetaChecksumValid` 唯一调用点在 `OugProbeMetaAds` 的 PASSIVE 检查之后 |
| 3 | **句柄生命周期** | 算法提供程序在 `DriverEntry` 打开一次、`OugFilterUnload` 关闭一次；hash 句柄每次用完立即 `BCryptDestroyHash`（含失败路径 —— 先 Destroy 再判 status） |
| 4 | **卸载顺序** | 先 `FltUnregisterFilter`（Filter Manager 会等所有回调结束后才返回），再 `BCryptCloseAlgorithmProvider`。顺序反了会导致并发哈希操作访问已关闭的算法句柄 |
| 5 | **失败路径不泄漏** | `BCryptCreateHash` 失败 → 直接返回 FALSE（无句柄可释放）；`HashData`/`FinishHash` 失败 → 仍执行 `BCryptDestroyHash` |
| 6 | **缓冲区边界** | `BCryptHashData(hash, Meta, OUG_META_OFF_CHECKSUM /* =24 */, 0)` 读的正是校验和之前的 24 字节；`meta` 已校验长度恰为 32 |
| 7 | **时序攻击** | 定长 8 字节 `RtlCompareMemory`，非时序安全。**评估：无风险** —— 校验值是公开可自行计算的 SHA-256 输出，攻击者不需要通过时序去猜 |
| 8 | **存疑不信** | `g_Sha256Alg == NULL` 或任何 BCrypt 失败都返回 FALSE → 计入 `AdsTampered` → `file_id` 不被采信。方向正确（宁可当"不可用"） |
| 9 | **结构体协议** | `C_ASSERT(sizeof(OUG_STATS) == 656)` 与 Rust 侧 `size_of == 656` 双向锁定，测试通过 |
| 10 | **复位完整性** | `RESET_STATS` 已补 `AdsTampered`（第 18 轮 S4 同类问题的先例，这次主动检查了） |
| 11 | **写路径** | **本轮仍然零写路径**：内核只 `FltCreateFileEx2(FILE_READ_DATA)` + `ZwReadFile` |

## 7. 本轮审计结论

**R1（上轮唯一的高危）已解决**，并留下了可验证的证据链：
算法两端交叉验证 → 黄金样本锁死 → 内核"验不了就不加载" → 验证脚本新增篡改检测步骤。

**新增 1 项中危（A1）**，但性质要说清楚：它不是"数据会被偷"，而是"文件可能被恶意搞成不可读"。
在 DLP 产品里这属于完整性/可用性风险，优先级低于机密性，且首选缓解（侧表）本来就在 M2 计划内。

**仍然不可上线的硬阻塞**：R4（驱动未实际加载验证）、R5（无 EV 签名）——都依赖外部条件。

**本轮再次确认"零写路径"**：改动全部是只读探测与计数，结构上不可能损坏用户数据。
