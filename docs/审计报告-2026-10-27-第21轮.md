## 2. 核实结果：此前结论基本正确，但有一处可以省钱

### 2.1 已证实的结论

| 此前的说法 | 官方原文 | 结论 |
|---|---|---|
| Win10 1607+ 内核驱动必须微软签名 | "Starting with Windows 10, version 1607, Windows will not load any new kernel-mode drivers which are not signed by the Dev Portal." | ✅ 准确 |
| 注册 Dev Portal 必须 EV 证书 | "an EV code signing certificate is required to establish a dashboard account" | ✅ 准确 |
| attestation signing 不需要 HLK | "you can submit your drivers for attestation signing, which does not require HLK testing" | ✅ 准确 |
| 关 Secure Boot 可加载受信任 CA 签的驱动 | 例外条款："Secure Boot is off in the BIOS" | ✅ 准确 |

### 2.2 本轮新发现（对成本有实际影响）

> "Although Microsoft strongly recommends that you sign individual submissions with an EV certificate,
> you can sign submissions with an **Authenticode signing certificate**. The Authenticode certificate must be
> registered to your Partner Center account."

**含义**：账号上绑一个 EV 证书满足注册门槛后，**每次提交时签包的证书可以是普通 Authenticode 证书**。

**影响**：
- 不必给每个开发/构建环境配 EV 硬件令牌；
- EV 令牌只需一个人保管、仅用于账号验证；
- 可以少买几张证书。

这条此前没有被记录，属于本轮核实的净收益。

### 2.3 官方认可的 CA 名单已确认

Certum / DigiCert / GlobalSign / IdenTrust / Sectigo / SSL.com —— 已写进文档，避免采购到无法通过账号验证的证书。

## 5. 结论

**本轮零代码变更、零风险引入。**

更重要的是：通过核实外部文档，纠正了"EV 证书要配到每个构建环境"的隐含假设，避免多买证书。
这类"把凭经验写下的话拿去对照官方原文"的核实，本身就应该纳入常规审计——**假设不核实，就会变成成本或事故。**

**唯一需要澄清的是交付场景**（对外销售 vs 内网自用），它决定是否真的必须走微软签名。已向用户提问。
