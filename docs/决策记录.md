## 2. 2026-10-26 · 系统文件零影响（硬保护）+ Windows 全版本兼容

**用户原话**：

> 「这个有一点要考虑的就是不要影响到系统本身的文件，我们主要是使用windows系统，但可能windows的各个版本以及服务器版本都有可能会使用」

### 2.1 落地（代码）

- `core::rules` 改为**三级判定**：硬保护（`builtin:system`，**任何规则不可覆盖**）→ 软排除（`builtin:default-exclude`，**规则之前**放行）→ 规则集排除 → 规则（优先级降序）→ 默认动作。
- 硬保护覆盖：`\Windows\`、`\WINNT\`（老系统）、`\Program Files\`、`\Program Files (x86)\`、`\$Recycle.Bin\`、`\System Volume Information\`、`\Config.Msi\`、`\Documents and Settings\`；盘符根 `X:\boot|efi|recovery|perflogs|$WinREAgent`；系统文件 `pagefile.sys`、`hiberfil.sys`、`swapfile.sys`、`dumpstack.log.tmp`、`ntuser.dat`、`ntuser.ini`、`bootmgr`、`bootnxt`。
- **不绑定 `C:`**（Windows 可装 D 盘）；**盘符根才生效**（`D:\Work\boot\` 不误伤）；UNC 共享盘不按盘符根处理。
- 软排除覆盖 Temp / AppData 缓存 / `.git` / `.svn` / `.hg` / `node_modules` / `__pycache__` / `.vs`；**ProgramData 有意不内置**（常放业务数据，由显式规则决定）。
- 公开 `is_hard_protected` / `is_soft_excluded` / `system_protection`，供服务端校验 `watch_roots` 与面板提示。

### 2.2 对两个决策的影响（强化结论）

- **加密层级**：更坚定选 **A 级用户态**。B 级（minifilter）工作在文件系统层，与系统更新/杀软/文件系统行为的耦合正是"影响系统"的主要风险源（蓝屏最典型），且每个 Windows 版本都要单独验证内核行为；A 级只依赖稳定的用户态 API，天然满足"不影响系统"。
- **算法**：更坚定选 **AES-256-GCM**。AES-NI 让加密的 CPU 开销可忽略（服务器批量场景尤其重要）；SM4 只能软件实现，批量加密时明显占 CPU，与"不影响系统运行"冲突。

- `cargo test -p pek-outguard-core`：**43 passed / 0 failed**（新增 7 项系统保护区用例，含"故意配 `C:\Windows` 加密规则仍不加密"的反证）

**用户原话**：

> 「那如果要申请解密并分享出去的这种场景有考虑到么？」

**此前状态**：只有需求预留（`FR-S-08`、`Og_Approval` 表、`/api/client/approval` 接口），没有设计细节。

**本轮补齐**（新文档 `docs/外发审批与外发包设计.md`）：

- 把"分享"拆成四条路径：**内部同事（直传 `.ogd`，无需审批）** / 外部外发包 `.oge` / 完全解密（最高审批）/ 受控网页预览。
- **关键决策：外发包由客户端本机生成，服务端只签发授权令牌**——文件本体不出网、服务端不解密。
- 外发包 `OGE1`：OGD1 容器 + 明文头（接收方/有效期/次数/水印/令牌签名）+ **打开密码派生的 KEK 包裹 DEK**（PBKDF2-SHA256 60 万次）；包与密码分渠道发送。
- 查看器：单 exe 免安装；PDF/图片/文本内置预览不落盘；Office 转 PDF 后外发。
- 吊销：宽松（本地校验 + 联网回执）/ 强管控（每次打开联网校验）。
- **如实声明边界**：明文离开受控体系即不可控；查看器可被逆向，强约束必须靠联网校验；截图/拍照无法阻止，水印用于追溯与威慑。

**分期**：M1 继续"内部转发天然支持"，M2 做完整外发链路，不打乱 M1。

## 4. 2026-10-26 · Server 端形态：Tauri 桌面外壳（非服务本体）

**用户原话**：

> 「Server端可以考虑Tarui吧」

### 4.1 决策

- **采纳 Tauri**：作为**可选桌面管理端**（`admin/`，M2），加载与浏览器完全相同的一套面板。
- **服务本体仍是 HTTP 服务**：星尘托管、无头运行、多角色/远程访问；不把 Tauri 放进服务进程。
- **面板保持纯静态 + HTTP 优先**，不依赖 Tauri IPC —— 随时可退回浏览器。
- **单机版**（Tauri + sidecar + SQLite）作为 M3 可选发行形态，面向无需独立服务器的小客户。

### 4.2 理由

1. 服务器常驻且无人登录时 Tauri 窗口无法渲染，与星尘托管/服务化冲突；
2. 审批人、审计员需要浏览器/手机访问，桌面外壳会挡路；
3. 服务与 UI 同进程会放大故障域（UI 崩溃 = 服务不可用、升级必须带 UI）；
4. 但桌面外壳确实解决"输地址麻烦、无通知、无托盘"，且**零重复开发**（同一份 `server/res` 面板）。

### 4.3 依赖提醒

- WebView2：Win10 1803+/Win11 自带；**Server 2016/2019 需预装 Evergreen Runtime**（安装包内置 bootstrapper）。
- Tauri 2 构建期需 Node.js；产物 `.msi`/`.exe` 约 5–10 MB。
- 单机版 sidecar：`pek-outguard-server.exe` 作为 externalBin。

### 4.4 验证

- 本轮仅架构定稿（`docs/架构设计.md` 第 13 章），**未引入 Tauri 工程**（避免未验证的构建链进入仓库）。

## 6. 2026-10-26 · 人员与设备管理 + 外发形态澄清

**用户原话**：

> 「Server端要有人员管理功能，Client要把每台电脑的一些基础数据能当惟一码的到Server做存储处理，Server端会配置每一个Client的用户名和权限，以及相应的部门等管理。外发包没有密码吧，这个是解密之后就可以直接发出去的吧」

### 6.1 人员与设备管理（设计 + 代码）

- **服务端新增**（FR-S-13/14/15）：人员档案（姓名/工号/部门/职位/联系方式/状态/角色）、部门树（含负责人）、**终端 ↔ 人员多对多绑定**（支持多人共用一台电脑）、终端策略组与功能权限（是否允许申请解密/外发/离线）。
- **三种身份分开**：面板登录用户（管理员/审批人/审计员，走 Pek.RAdmin 用户与权限）、**员工档案**（`Og_Staff`，无密码，按终端上报的 Windows 用户名匹配）、**终端**（`Og_Client`，机器码为唯一码）。
- **设备唯一码落地**（FR-C-19）：`core::machine::machine_id(SMBIOS UUID, MachineGuid, 卷序列号)` → SHA-256 前 128 位；格式差异归一化（大小写/大括号/连字符）；三者全空报错；只采到一项也能生成；不加安装随机盐（否则重装后认不出同一台机器）。虚拟机克隆会撞码 → 面板提示人工绑定。
- **协议扩展**：`RegisterRequest` 增加 `hardware`（CPU/内存/磁盘/构建号/域）、`loggedUser`、`ip`、`mac`、`installedAt`；旧客户端 JSON 仍可解析（向后兼容测试）；心跳新增 `ip/mac/hardware` 变化项（未变化不发）。
- **数据表**：`Og_Department`、`Og_Staff`、`Og_StaffClient`；`Og_Client` 扩展为一台电脑的完整资产台账。

### 6.2 外发形态澄清（重要）

**用户理解校正**：外发包 **≠** 解密后的文件。

| 形态 | 对方需要什么 | 密码 | 失控风险 |
|---|---|---|---|
| **完全解密（主路径）** | 无（就是原始 docx/pdf） | 无 | 高（可任意转发） |
| **外发包 `.oge`（可选）** | OutGuard 查看器（免安装 exe） | **默认无**，可设 | 低–中（靠有效期/次数/水印/回执） |

- 按用户口径调整：**"审批通过 → 解密 → 直接发"列为最常用路径**（不走查看器、不设密码）。
- 外发包的**密码改为可选项**（需要防转发时才设，且与包分渠道发送）。
- 需求与外发设计文档已同步：完全解密列"最常用"，外发包默认无密码。

## 7. 2026-10-26 · 外发包密码策略（三档）

**用户原话**：

> 「外发包需要弄解密密码嘛？还是说什么样的？」

### 7.1 结论（已写入外发设计 5.1/5.2）

| 档位 | 密码 | 适用 | 保护强度 |
|---|---|---|---|
| **无密码（默认）** | 不需要 | 普通商务往来、"让对方看一眼" | 格式保护 + 行为管控（有效期/次数/水印/回执） |
| **随机密码（敏感件推荐）** | 系统生成 8–12 位，审批人可见 | 合同、图纸、报价 | PBKDF2-SHA256 60 万次 + AES-256-GCM |
| **固定密码** | 审批人设定 | 与固定客户的长期约定 | 同上（密码复用有风险） |
| （可选）绑定接收方 | 手机号后 4 位 / 工号 | 免传递场景 | 弱口令 |

- **密码必须与包分渠道发送**（包走邮件/IM，密码走电话/短信），否则等于没设。
- **技术真相**：无密码外发包的 DEK 用查看器内置固定 KEK 包裹 → 只做格式保护，**逆向可破**；有密码才是密码学保护。此结论已如实写入文档（安全边界第 5 条）。
- 三档建议：普通商务 → 无密码；敏感件 → 随机密码；必须可控 → 受控网页预览（不落盘）。

## 11. 2026-10-27 · 离线可用（断网照常保护，联网自动补同步）

**用户原话**：

> 「有一点要留意，如果网络不通的情况下，Client 要用本地已同步的规则，当连接上后再定时同步 Server 的」

### 11.1 设计口径

| 场景 | 行为 |
|---|---|
| 断网时保存受控文件 | **照常自动加密**（用 `Data/state.json` 缓存的规则集与密钥） |
| 断网时产生的审计 | 进本地队列（上限 5000 条），联网后按 200 条/批补传 |
| 断网时启动客户端 | **不退出**，用缓存策略启动监控（没有缓存则告警空转，联网后自动启用） |
| 首次安装就断网 | 不崩溃；每 60 s 重试注册，联网后自动补齐身份+策略+监控 |
| 恢复联网 | 心跳探测到后自动补同步（版本比对）+ 补传事件 + 重建监控（只在根变化时） |
| 长期离线（拔网线绕过） | 超过服务端 `OfflineGraceDays` 后**拒绝解密/受控打开**，但**自动加密继续**（用户数据不丢） |

### 11.2 落地

- 协议：`PolicyBundle.offline_grace_days`（服务端 `OfflineGraceDays`，默认 7 天；`0` = 不限制）。
- 状态：`ClientState.last_online`（离线判定基准）+ `offline_reported`（离线告警去重）+ `offline_secs/offline_days/offline_grace_days/offline_exceeded/offline_block_reason`。
- 运行时：`prepare_online`（非致命）、`mark_online`（在线状态变化记一条日志）、`retry_register_if_needed`（断网安装补注册）、`reconcile_watch`（监控根与策略每轮对齐）、`check_offline`（超期告警一次）。
- 解密闸门：`ops::decrypt_file` 开头校验离线宽限；`open_file` 走同一路径，自动加密不受影响。
- `status` 展示：`连接：`（在线 / 最近通信 N 分钟前 / 离线约 N 天）+ `离线宽限：7 天（剩余 N 天）`。

## 12. 2026-10-27 · 受控打开闭环 + 文件关联 + 安全阀（不碰正式文件）

**用户原话**：

> 「这里有个问题吧，安装了 Client 的通过其他软件不能直接打开吗？岂不是每次都要先解密才能打开？」
>
> 「需要无感」
>
> 「而且目前调试阶段不要影响到我正常的使用，也就是在没有完整确认无误不要加密我正式的文件」

### 12.1 先把概念说清（受控打开 ≠ 申请解密）

| 动作 | 需要审批 | 能干什么 |
|---|---|---|
| **受控打开**（双击 `.ogd`） | 不需要 | 解密到受控临时目录交给 Office；保存**自动回写成密文**；离线宽限期内照常用 |
| **申请解密 / 申请外发** | 需要（联网） | 拿到**干净明文**（外发给没装客户端的人 / 永久明文存档），高危，必须审批 |

所以「实际都是加密文件在用」是设计目标，但**不影响日常办公**——前提是受控打开闭环必须做对。

### 12.2 修掉的致命缺陷：编辑后改动丢失

原实现 `open` 只是“解密到临时目录 → 交给 Office”，用户改完保存：
改动只落在临时明文上，**密文里还是旧内容**（用户白干），且明文永久残留。

现在的闭环（`client/src/opensession.rs`）：

1. 打开时解密为 `{临时目录}/{原名}.{会话ID}.{扩展名}`，会话登记到 `Data/sessions.json`（**绝对路径**）；
2. 常驻服务监听临时目录，改动去抖 3 s 后用**原容器同一把策略密钥**重新加密，原子替换回 `.ogd`（保留原密级/创建者/规则）；
3. **内容哈希去重**：打开文件本身也会触发 Modify（访问时间/锁文件），内容没变不重复加密；
4. 会话超时（2 小时且近 10 分钟无改动）才清理明文——不删正在编辑的文件。

实测（真实文件）：

```
受控打开：...\季度报告.pdf.ogd → ...\季度报告.a13c00f1.pdf（会话 a13c00f1）
受控打开回写完成：... 第一季度 v1（37 字节）
受控打开回写完成：... 第二版 v2（75 字节）      ← 用户在 Office 里改的
解密验证：内容 = “季度报告 第二版 编辑后内容 v2 - 用户在 Office 里改的”
```

### 12.4 安全阀（用户硬要求：调试期不碰正式文件）

| 阀 | 默认 | 效果 |
|---|---|---|
| **`Mode = "dry_run"`** | ✅ 开启 | 只按规则判定并记日志，**不加密/不移动/不删除任何文件** |
| **`AllowRiskyRoots = false`** | ✅ 开启 | 桌面/文档/下载/用户目录本身/盘符根/系统目录 → **自动跳过并告警** |

## 16. 2026-10-27 · 密文写入时机（打开不该重写密文）

**用户原话**：

> 「这个密文应该不会经常变吧？」

### 16.1 实测发现的真问题

原去重只靠**内存表**（`Inner.sealed`），服务重启即失效。实测：

```
读取前：2026年度合同.txt.ogd  628 字节  13:55:53
读 10 次 + 列目录 10 次
读取后：2026年度合同.txt.ogd  628 字节  13:56:03   ← 时间戳变了！
```

原因：ProjFS 的 **hydrate**（用户打开文件时把内容填充到本地缓存）也会产生 `Modify` 事件，
服务重启后内存去重表为空 → 判定"内容变了" → **整文件重新加密**。
后果：① 用户只是"看了一眼"就产生写放大；② 备份/同步工具每次都认为文件变了要重传；③ SSD 额外磨损。

### 16.2 修法：以密文库容器头为准

容器头里本来就记了 `plainSha256`。去重改成：

```
内存表命中 → 用内存哈希（快路径）
内存表未命中 → 读密文库容器头的 plainSha256 比对（准，重启后依然有效）
```

内容一致就**只降级占位符**（必须做，否则磁盘留明文），不写密文库、不记审计。

### 16.3 修复后实测

```
读取前：628 字节  13:56:30
读 10 次 + 列目录 10 次
读取后：628 字节  13:56:30   ← 一个字节都没变

修改内容（Ctrl+S）→ 622 字节  13:56:46   ← 只有内容真变才写
再连读 5 次       → 622 字节  13:56:46   ← 仍然不变
```

### 16.4 写入时机的完整口径（交付文档要写）

| 操作 | 是否改动密文 |
|---|---|
| 打开 / 浏览 / 搜索 / 复制 / 列目录 | ❌ **完全不变** |
| 保存（内容真的变了） | ✅ 写一次 |
| 导入新文件 | ✅ 写一次 |
| 服务重启 | ❌ 不写（不再因内存表清空而重加密） |

**仍需注意**：每次保存是**全文件重加密**（OGD1 格式的分块 AAD 绑定头部哈希，不支持局部重写）。
所以大文件（几百 MB 的 CAD）每次 Ctrl+S 都会全量读写一遍。后续可做分块增量格式（需 V2 容器）。

### 16.5 部署建议（减少无谓 IO）

- `Data\Vault` **不要**放在云同步盘（OneDrive/坚果云）里，否则每次保存都会触发上传；
- 杀毒软件建议把 `Data\Vault` 加入**实时扫描排除**（密文扫描无意义，只增 IO）；
- 备份走定时快照（下一轮做 `vault backup`），不要用"逐文件实时同步"。

## 17. 2026-10-27 · 性能与安全收口（大文件不吃内存 · 磁盘不留明文 · 保存不全盘扫描）

> 用户原话（本轮要求）：
> 「请继续，这个一定要让用户无感知，且不会影响实际使用性能，也不会让操作变复杂，而且绝对要安全」
> 上一轮追问：「这个密文应该不会经常变吧？」（已由第 16 节回答并验证）

### 17.1 本轮揪出的 6 个真问题

| # | 问题 | 后果 |
|---|---|---|
| P1 | 打开文件时 `plain()` 把**整个文件读进内存** | 500 MB 图纸峰值近 1 GB，进程可能被 OOM 杀掉 → 服务挂 |
| P2 | 中间版本改成"解密到磁盘缓存 `VaultCache/*.plain`" | **明文落在磁盘上**——对 DLP 产品是硬伤（比 OOM 更严重） |
| P3 | `seal_one()` 用 `std::fs::read` 读全文再哈希 | 保存大文件时同样吃满内存 |
| P4 | `seal_dirty()` 每次保存**全盘扫描**整个安全区 | 目录文件一多，保存就卡；与"资源与带宽"约定冲突 |
| P5 | 命令行 `secure-area run` 与后台服务**各写一份**保存监控 | 改一处漏一处（CLI 那份还在全盘扫描） |
| P6 | 落位密文用裸 `std::fs::rename` | 杀软/备份恰好占着目标文件时"拒绝访问"直接失败，明文留到下次 |

**还有一个更隐蔽的**：

| # | 问题 | 后果 |
|---|---|---|
| P7 | 读完之后 ProjFS 把**明文留在本地**，永远不收回 | 用户看一眼就关掉的文件，明文长期躺在磁盘上，DLP 形同虚设 |

### 17.2 改法（逐条对应）

- **P1/P2 → 按需区间解密**：新增 `core::container::decrypt_range(path, kek, offset, len, out)`，
  按分块直接定位（`data_start + index * (4 + chunk + 16)`），只解应用真正要看的那几块。
  **不写任何明文缓存**，内存占用等于一次回调的数据量。
  旧的 `VaultCache` 目录在启动时**一次性删除**（清理历史版本残留的明文）。
- **P3 → 全流式**：`core::crypto::sha256_file()` 256 KB 缓冲流式哈希；加密输入直接用文件句柄。
  保存 300 MB 文件，进程内存不变。
- **P4 → 精准路径**：新增 `seal_path(&Path)`，只处理监控到变化的那一个文件；
  `seal_dirty()` 降级为**启动兜底 + 手工清扫**。
- **P5 → 抽出公共件**：`runtime::attach_seal_watch(area, root)`，CLI 与服务共用同一份（含空闲脱水线程）。
- **P6 → 原子替换**：改用 `dhrust::io::safe_replace_file`（内部带占用重试）。
- **P7 → 空闲脱水**：记录"被读过哪些文件"（内存表），
  `dehydrate_idle(60s)` 把 60 秒没再被读的文件降级回占位符。
  **关键发现**：`PrjUpdateFileIfNeeded` 对"内容未变的完整文件"是 **no-op**，
  必须给它一个**不同的 ContentID**（`placeholder_for(..., seed)`）才会真正丢弃本地明文。
  不加这一条，日志说"已降级"但 `fsutil` 能看到 300 MB 明文原封不动躺在盘上。

### 17.3 两个避免"抖动"的细节（不然性能反而更差）

1. **水化（hydrate）不算"保存"**：打开文件也会产生 `Modify` 事件。
   若立刻降级，应用下一秒又要去召回 → 读 300 MB 变成反复水化/脱水。
   现在的口径：**内容与密文库一致时不立刻降级**，交给空闲脱水；**内容变了才加密并立即降级**。
2. **同一版本短时间内只算一次哈希**：`recent` 表按（大小 + mtime + 5 秒窗口）去重。
   否则读一次大文件会白算十几次 300 MB 的 SHA-256。

## 18. 2026-10-27 · 结论性判断：ProjFS 做不到"打开期间不落明文"（附替代路线与许可证核实）

> 用户原话：
> 「如果打开时是明文，那这个方案就不可行了。」
> 「换其他开源方案？」

### 18.1 结论：ProjFS 这条路对 DLP 是死路

不是实现问题，是机制问题：**ProjFS 的 `PrjWriteFileData` 是把数据写进 NTFS 的水化缓存**——
只要应用用 `ReadFile` 读文件，Windows 就会把这段数据落成本地磁盘数据，这正是它读得快的原理。
没有任何启动选项能关掉这个行为（`PRJ_STARTVIRTUALIZING_OPTIONS` 只有负路径缓存之类的开关）。

我们能做的只是把窗口期从"永远"压到"空闲 60 秒"，**做不到零**。
对一个要防"内部人员用别的软件拷走明文"的 DLP 产品，这不够。

**因此：ProjFS 只能作为"过渡演示形态"，不能作为交付形态。** 第 17 节的性能优化与安全收尾全部保留有效
（容器/密钥/策略/审计/按需区间解密都是底层能力，换呈现层后继续用）。

### 18.2 替代路线（三选一，均已核实事实）

| | **Dokany（推荐）** | WinFsp | minifilter 自研驱动 |
|---|---|---|---|
| 形态 | 用户态文件系统，挂盘符/目录 | 同左 | 内核驱动，全盘透明 |
| 打开期间落明文 | ❌ **不落**（read 回调当场解密，数据只过内存） | ❌ 不落 | ❌ 不落 |
| 驱动签名 | **官方已签名**，装 msi 即可，**无需我们签名** | 官方已签名 | **需自备 EV 证书 + 微软 attestation 签名** |
| 许可证（关键） | **LGPL**（dokan2.dll / dokan2.sys / 安装器）+ MIT（dokanctl、样例）→ **闭源商业产品可用**（动态链接不传染） | GPLv3 + FLOSS 例外 + **商业许可另售**；Rust 绑定 `winfsp` crate 是 **GPL-3.0**（会传染） | 自有 |

| 工作量 | 中（约一个模块 + 回调映射 + 调试） | 中 | 大（3~5 倍，蓝屏风险，需驱动测试机） |

**行业先例**：开源透明加密产品 **Cryptomator** 的 Windows 端就是"WinFsp 或 Dokan + 实时加解密 + 容器"这一套，
说明该架构可行且成熟。（它不选 GPL 绑定的方式，而是按需加载驱动 DLL。）

### 18.3 推荐

1. **呈现层换 Dokany**（LGPL，不用买许可、不用签驱动）。
2. **Dokan 只保证"安全区里的文件不落明文"**；"另存到桌面"仍靠 `WatchRoots` 再加密兜底——
   这一点必须写进交付文档，不能让客户以为全拦。
3. **要连"另存到别处"一起拦**，只有 minifilter；那是第二阶段（需 EV 证书），不是现在能做的。
4. 复用清单：容器 OGD1、密钥体系、策略下发、审计、`container::decrypt_range`（正好就是 Dokan read 回调要的）
   **全部复用**；报废的只有 `secure_area.rs` 这一个模块（ProjFS 回调层）。

### 18.4 本轮顺带修掉的两个真实漏洞（与呈现层无关，换 Dokan 前也必须修）

**漏洞 1：服务被强杀/升级后，安全区永久起不来**

实测复现：强杀进程后目录里留下 ProjFS 占位符（属性 4204064 与 9760 两种形态），
而 `check_area`/`start` 要求"目录必须为空"→ **一次崩溃就让安全区再也启动不了**，用户看到的是文件全没了。

修法：
- `is_placeholder()` 补上第二种形态（`ReparsePoint + Sparse`；provider 停止后 ProjFS 会撤掉 `RECALL_ON_DATA_ACCESS`）；
- `check_area()` 只拒绝**真正的明文实体文件**，允许残留自家占位符；
- `start()` 删除重复的"必须为空"检查，改为复用 `check_area()`（两套口径打架正是根因）；
- `absorb_existing()` 跳过占位符（provider 未启动时读它没有意义，还会搞乱 ProjFS 的脏状态）。

实测：强杀后 `secure-area status` 报"可直接启用"，重启后 `采购合同.docx`(5,242,880 B)、
`big.bin`(314,572,800 B) 都能正常读出，**数据未丢**。

**漏洞 2：服务正常停止时明文留在磁盘上**

`Drop` 里原来是"先 `PrjStopVirtualizing` 再释放"——ProjFS 一停，已水化的文件就退化成实体文件，
明文留在盘上（升级、重启时最容易漏）。修法：`Drop` **先** `dehydrate_idle(0)` + `seal_dirty()` 收回明文，
再停止虚拟化。

## 20. 2026-10-27 · 保护边界的最终结论：受控区是"保险箱"，不是"全盘防泄漏"

> 用户原话：「那岂不是明文文件还是在原来的地方随时可见」

### 20.1 结论：用户说得对

| 事实 | 说明 |
|---|---|
| **受控区（ProjFS/Dokany）里没搬走的文件，明文照旧在原位置** | 受控区只是"新增一个箱子"，箱外的东西一概不管 |
| **用户日常新写的文件仍在原目录，都是明文** | 除非落点本身在受控区内，或命中 `WatchRoots` 自动加密（变成 `.ogd`，文件名会变） |
| **即使用户态方案把文件搬进箱子，应用打开时明文仍会落盘** | ProjFS 是"水化到本地"；受控打开是"解到临时目录"。**用户态方案无法做到零明文落盘**，区别只是窗口期长短 |

**因此：任何用户态方案（ProjFS / Dokany / WinFsp）都只能实现"机密文档保险箱"，
实现不了"员工电脑上所有文档自动加密、他自己都不知道"这种全盘防护。**

1. **不能把 ucrt 头加进内核编译** → `corecrt.h(623): error C2371: _locale_t 重定义`。

2. **WDK 26100 移除了 `IRP_MJ_OPERATION_END_OF_QUEUE`**，结束标记改名 `IRP_MJ_OPERATION_END`（`(UCHAR)0x80`）。
3. **`FLT_REGISTRATION` 字段顺序写错会蓝屏**：第 6 个是 `FilterUnloadCallback`、第 7 个才是
   `InstanceSetupCallback`。最初把 InstanceSetup 填到第 6 位，卸载时会以错误签名调用 → 已在代码里写注释锁死。
4. **卸载回调签名**必须是 `NTSTATUS(FLT_FILTER_UNLOAD_FLAGS)`；minifilter 不要用 `DriverObject->DriverUnload`。
5. **`sc.exe create` 在 PowerShell 里极易报 1639**（引号嵌套被打散）→ 改为**直接写注册表**创建服务项，更可控。
6. **含中文的 `.ps1` / `.c` 必须 UTF-8 with BOM**，否则 PS5.1 按 GBK 解析报语法错、cl 报 C4819。

### 21.4 M0 驱动做了什么（安全边界）

- **只计数，不修改任何读写数据**：`IRP_MJ_CREATE/READ/WRITE/SET_INFORMATION/CLEANUP` 五个回调
  全部 `return FLT_PREOP_SUCCESS_NO_CALLBACK`，**零数据风险**；

## 23. 2026-10-27 · M2 加密算法选型的硬事实（CNG 探测结论）

> 结论先行：**M2 不用 CNG 的 XTS/CTR，改用「AES-ECB + 自实现 XTS」**。
> 依据是实测，不是偏好。

### 23.1 三条实测结论

| 探测项 | 结果 | 影响 |
|---|---|---|
| `BCRYPT_XTS_AES_ALGORITHM`（"XTS-AES"） | 能打开（`BlockLength=16`，`MessageBlockLength` 可设 512/4096），但 `BCryptEncrypt` **一律返回 `0xC000000D`(STATUS_INVALID_PARAMETER)** | 试了 key 长度(32/64) × 数据单元(512/4096) × 输入长度(16/100/512/1024) × 属性设在 hAlg/hKey × 4/8 字节，**共 16+ 组合全失败** |
| `ChainingModeCTR`（AES 的 CTR 模式） | 设置即失败 `0xC000000D` | CNG 不提供 CTR |
| `AES` + `BCRYPT_CHAIN_MODE_ECB`（默认链模式） | **可用 ✅** | `key=0102..20`、明文全 0 → 密文 `a73c5576667b7b43a23a9fd930b5465d` |

### 23.2 为什么这不是坏事

CNG 的 XTS 用法不透明（文档只给了算法标识，没有参数要求），继续猜的代价是：
一旦内核里参数写错，**用户的文件就再也解不回来**——这是 DLP 产品最不能接受的失败模式。

改用 AES-ECB 自实现 XTS 反而更可控：

| 对比项 | 直接用 CNG XTS | **AES-ECB + 自实现 XTS** |
|---|---|---|
| 依赖 | 未知参数的 CNG 实现 | 只用最基础、已实测可用的 AES-ECB |
| 内核/用户态一致 | 两端都用 CNG，但内核 CNG 支持面未知 | 内核用 BCrypt-ECB、救援工具用 Rust AES，**同一套 tweak 逻辑**，可逐字节交叉验证 |
| 出错可控性 | 黑盒 | 算法透明，可用标准测试向量 + 性质测试锁死 |
| 救援工具 | 依赖驱动 | **纯用户态就能解密**（这是最关键的） |

XTS 本身只需两步：`T = AES(key2, tweak)`，然后每块 `C = AES(key1, P ⊕ T) ⊕ T`，`T = mul_α(T)`。
GF(2^128) 乘 α 只是"左移 + 条件异或 0x87"，60 行以内。

### 23.3 交叉验证锚点（已验证的一对）

```
AES-256-ECB，key = 0102...20（32 字节），明文 = 全 0（16 字节）
密文 = a73c5576667b7b43a23a9fd930b5465d      ← 来自 Windows CNG
```

Rust 侧用 `aes` crate 加密同样输入**必须得到同一串**。这一条对齐了，就说明两端的 AES 底座一致；
再对齐 tweak 逻辑，XTS 就能互通。

## 24. 2026-10-27 · M2 地基：XTS 加解密实现 + 与 Windows CNG 交叉验证通过

> 用户当时说「现在不方便重启」，所以先做不依赖重启的那部分——
> 而这部分恰好是"数据最后一道保险"：**驱动哪天出问题，靠它把文件救回来**。

### 24.1 实现（`core/src/xts.rs`）

```text
key      = 64 字节（两个 AES-256 密钥：key1 做数据、key2 做 tweak）
file_id  = 8 字节文件身份
tweak i  = AES_ECB(key2, file_id || block_index_be64)
C i      = AES_ECB(key1, P i ⊕ tweak i) ⊕ tweak i
P i      = AES_ECB⁻¹(key1, C i ⊕ tweak i) ⊕ tweak i
```

**密文长度 = 明文长度**（对应用完全透明）；任意 16 字节对齐的偏移都能 **O(1) 直接定位**。

### 24.2 与 IEEE 1619 标准 XTS 的差别（必须诚实说明）

| | 标准 XTS | 本实现 |
|---|---|---|
| tweak 生成 | 初始 tweak 反复乘 α 形成链 | `AES(key2, file_id ‖ block_index)` |
| 随机访问 | 跳到第 N 块要迭代 N 次（大文件不可接受） | **O(1)** |
| 安全性依据 | tweak 唯一 | **tweak 唯一**（每 (文件,块) 都不同） |
| 完整性认证 | 无 | 无（与 XTS/EFS/BitLocker 同级别） |

换成 `AES(key2, …)` 的直接原因：**CAD/数据库那类随机读写，不能容忍"跳到文件尾部要迭代几千万次"**。
安全性上没有降级——两者都不会出现"相同明文块得到相同密文块"。

### 24.3 交叉验证（这一节是重点）

驱动最终用 Windows CNG 的 AES-ECB，救援工具用 Rust 的 `aes` crate。
**两套代码必须产出完全相同的密文，否则驱动出故障时文件就救不回来了。**

做法：用 `driver/xref-xts.ps1`（C# + `bcrypt.dll`，与 Rust 完全独立实现）算出参考值，
再在 Rust 测试里断言同样的数值。

```

            CNG（内核侧）                        Rust（救援工具侧）
tweak[0]    b2d86a4b8145cb41b78ce0654b0183e0     一致 ✅
tweak[1]    b8bbec34d9537e3d6e3f46c98cfe998b     一致 ✅
密文[0]     3c7c2c4da3ac6d528a970f90b393d252     一致 ✅（明文全 0）
密文[1]     6471017c2835b8e68b8b1b4b71c6e7e4     一致 ✅（明文 0001..0f）
块4 密文    8072b0db5099ed87b560c56a0128bb1f     一致 ✅（offset=64 随机访问）
```

## 25. 2026-10-27 · 救援路径：文件身份存 NTFS ADS + 离线解密工具（驱动坏了也能救）

### 25.1 用户要求（原话）

> 「请继续，这个一定要让用户无感知，且不会影响实际使用性能，也不会让操作变复杂，而且**绝对要安全**」

「绝对要安全」在工程上的落地不是我保证代码没 bug，而是：**任何一环出错，数据都必须还能拿回来**。透明加密最怕的失败模式就是"驱动挂了、文件成了谁也不认识的密文"——那等于把公司的文件锁死了。所以救援路径不是附属功能，是这条技术路线的准入条件。

### 25.2 文件身份存哪里：三个方案对比

| 方案 | 优点 | 致命问题 |
|---|---|---|
| 把 file_id 写进文件头 | 自包含 | **改变文件大小** → 违反"对应用完全透明"（Word 会看到文件长大、tail 会错、数据库/映射文件直接坏） |
| 侧表（按路径记） | 不碰文件 | 改名/移动/复制即失配；跨机器一律失效 |
| **NTFS ADS（本方案）** | 主文件**大小与内容格式不变**；跟随文件在同卷内移动/改名；多流是 NTFS 原生特性 | FAT32/exFAT/U 盘丢失；部分备份工具不保留 |

选 **ADS `file:oug`（32 字节）**，并已实测（见 25.4）：写入后主文件内容与大小**完全不变**。

### 25.3 元数据格式（32 字节，锁定）

| 偏移 | 长度 | 含义 |
|---|---|---|
| 0 | 4 | 魔数 `OGM1` |
| 4 | 1 | 版本 = 1 |
| 5 | 1 | 标志位（bit0 = 已加密） |
| 6 | 2 | 保留 |
| 8 | 8 | **file_id**（XTS tweak 的基值，随机生成） |
| 16 | 8 | 加密时间（Unix 秒） |
| 24 | 8 | **校验和** = `SHA-256(前 24 字节)[0..8]` |

**校验和是硬要求**：救援工具运行时驱动已经坏了，此时任何"猜"都是灾难。校验失败必须**明确拒绝解密**并说明原因，绝不静默输出垃圾。`rejects_tampered_file_id` 测试守住这条。

### 25.4 实测（真实文件，端到端）

用 `core/src/xts.rs`（12,617 字节）当样本，固定密钥 `000102...3f`：

```
明文 SHA256 = 176EFADB...E4E5B731  大小 = 12617
rescue encrypt → 密文 SHA256 = 445B7757...1DD134C8  大小 = 12617
大小相同 = True   内容已变 = True          ← 透明加密的硬指标
rescue info  → file_id = 90a7b0156ba936ca；文件大小 12617（明文与密文等长）
rescue verify → 12617 字节全部校验通过
rescue decrypt --out out → 还原 SHA256 = 176EFADB...E4E5B731
逐字节一致 = True                          ← 救援闭环成立
```

### 25.5 密钥来源两档

| 场景 | 密钥来源 | 说明 |
|---|---|---|
| 本机救援（驱动坏了、Windows 还在） | 本机策略密钥 → `derive_xts_key`（HKDF-SHA256，info=`oug/xts/v1`） | 无需人工干预，一条命令即可 |
| 换机 / 灾难恢复 / 司法取证 | `--key-hex <128 hex>` 显式提供 64 字节 XTS 密钥 | 服务端可从主密钥重新派生，本工具**不联网** |

XTS 密钥与 OGD1 容器密钥用**不同的 HKDF info** 派生，互不可推导——即使某文件同时存在两种格式，也不会共用同一把密钥。

### 25.6 安全设计（写进代码注释的三条）

1. **永不覆盖原件**：`decrypt` 只写 `--out` 指定目录，且目标已存在时**拒绝覆盖**；
2. **加密先写临时文件再原子替换**：中途断电/失败，原文件完好（`safe_replace_file`，占用时重试）；
3. **等长强校验**：加密后若发现密文长度 ≠ 明文长度，**中止并删除临时文件**，绝不落盘一个尺寸不对的"密文"。

### 25.7 已知限制（必须交付给运维看）

- ADS 在 **FAT32 / exFAT / 多数 U 盘** 上会丢失 → 后续必须在客户端的复制/拖拽路径上**拦截**（M3 一并做）；
- 部分备份、同步、压缩工具不保留 ADS；
- ADS 丢失 ≠ 数据丢失：M2 会加 `Data/DriverIndex.db` 侧表（路径 → file_id），双保险；

## 26. 2026-10-27 · 性能实测（5.6× 提速）+ 批量体检 + 重启后一键验证脚本

### 26.1 用户要求（原话）

> 「目前还不能重启，可以继续推进下一轮吧」

这意味着本轮必须挑**不依赖驱动加载**、但又能推进产品的事。我选了最该先做的一件：**量出加解密的真实吞吐**——因为如果加解密慢，整个"透明加密"路线在用户体感上就是失败的，写再多驱动代码也没意义。

### 26.2 性能实测：为什么必须先量这个

透明加密的**每一次文件读写**都要过一次加解密。这不是"偶尔慢一下"，是持续的。所以吞吐量直接决定：

- 打开 20MB 的 PPT 是 9ms 还是 500ms；
- Ctrl+S 保存时用户会不会看到转圈；
- 杀毒软件全盘扫描时客户端会不会把 CPU 吃满。

**结论先行：够快，路线可以上。**

| 实现 | 加密 | 解密 |
|---|---|---|
| 逐块串行（每块单独调 `encrypt_block`） | 388 MiB/s | 390 MiB/s |
| **8 路批量（现实现）** | **2289 MiB/s** | **2290 MiB/s** |

**加速 5.6×**。用户真正感受到的数字：

| 文件大小 | 加解密耗时 |
|---|---|
| 1 MB | 0.4 ms |
| 5 MB | 2.2 ms |
| 20 MB | 8.7 ms |
| 100 MB | 43.7 ms |
| 500 MB | 218 ms |

普通办公文件（Word/Excel/PPT 绝大多数 < 20MB）**在 10ms 内**，用户完全无感。

### 26.3 为什么批量能快 5.6 倍（原因值得记住）

x86_64 的 AES-NI 指令**单条延迟 4 周期，但可以同时跑 8 条**。逐块调用 `encrypt_block` 时，每块都要等上一块的 AES 结果（串行依赖），流水线永远填不满 → 只跑到 390 MiB/s。改成一次喂 8 块，CPU 才能并行 → 2289 MiB/s。

**关键约束：密文必须一个字节都不能变。** 批量化只改"调用方式"，不改算法。为此：

- `core/tests/xts_perf.rs` 里保留了一份**逐块串行参考实现**，对 64MB 数据做逐字节对拍；
- 原有 `matches_windows_cng_reference_vectors` 继续守着与 Windows CNG 的一致性（批量化后仍然通过）。

同时加了**性能守门**：吞吐低于 500 MiB/s 直接测试失败，防止将来谁把优化改回去却没人发现。

### 26.4 顺手抓到的两个真 bug

**① 基准测试第一版的批量实现密文与串行版不一致。** 原因：`tweak` 用了**组内序号**而不是**全局块序号**（`base + i` 应为 `base + group_index * BATCH + i`）——第 2 组开始的密文全错。如果没有对拍断言，这个 bug 会一路带进驱动，等客户打开文件发现乱码才知道。**教训：任何"只改性能"的优化，都必须有逐字节对拍的断言。**

**② 第一版批量版反而更慢（0.77×）。** 原因：每 8 块做一次 `Vec::with_capacity` 堆分配，分配开销把并行收益全吃回去了。改用栈上定长数组（`[Block; 8]`）后才有 5.6×。**教训：微优化必须实测，不能靠直觉。**

### 26.5 `rescue scan`：批量体检（驱动崩了要知道"哪些文件是密的"）

驱动崩溃/卸载后，运维最先要回答三个问题：**哪些文件已加密、哪些一个标记都没有（＝漏了或明文外泄）、哪些标记坏了需要人工处理。**

```
rescue scan <dir> [--ext .docx,.xlsx] [--deep]
```

实测（4 个 docx/xlsx + 1 个 txt，其中 2 个已加密、1 个明文、1 个 ADS 被写坏）：

```
  方案B.docx —— 元数据魔数不匹配（不是本产品的加密标记）
```

## 27. 2026-10-27 · M2a：驱动读 ADS 拿文件身份 + 首轮安全审计（发现 1 个高危缺陷）

### 27.1 用户要求（原话）

> 「请继续下一轮，**每一轮做完之后要做审计，要包含安全审计**」

审计这条从本轮起成为**制度**：已写入 `.github/copilot-instructions.md` 流程段与用户记忆。
每轮收尾从"三件套"升级为**四件套**：决策记录 / **审计报告** / 记忆同步 / 回归汇报。

### 27.2 M2a 做了什么

命中受控规则的文件，驱动现在会**只读**打开它的 NTFS 备用数据流 `file:oug`，读 32 字节元数据，
校验魔数 + 版本 + 加密标志位，取出 `file_id`——这是 M2b 加解密真正需要的那个值。

**零写路径**：只 `FltCreateFileEx2(FILE_READ_DATA)` + `ZwReadFile`，不写、不删、不改属性。
结构上不可能损坏数据，这是本轮最强的完整性论证。

统计新增五项（`driver status` 可见）：

| 计数 | 含义 |
|---|---|
| `AdsHit` | 读到有效加密标记（文件确实已加密） |
| `AdsAbsent` | 没有标记 / 标记未置加密位（未加密） |
| `AdsBroken` | 有流但魔数/版本/长度不对（损坏，要人工处理） |
| `AdsError` | 打不开/读失败（权限异常、文件被删） |
| `AdsSkipped` | 本次没探测（IRQL 不合适，**不是错误**） |

### 27.3 技术难点：内核里怎么安全地打开"同一个文件的另一个流"

在 `PreCreate` 里发起新的 Create，最大的风险是**递归**——新 Create 又进入自己的 `PreCreate`，无限循环。

第一版方案用 `IoSetTopLevelIrp(FLT_TOP_LEVEL_IRP)` 做标记，**编译直接失败**：
WDK 26100 已移除 `FLT_TOP_LEVEL_IRP` 常量。

改用更干净的方案：`FltCreateFileEx2` 的 `Instance` 参数传 `FltObjects->Instance`，
I/O 就**从本实例下方发起**，根本不会进入自己的回调。`Instance` 为空时直接放弃探测。

这比标记法更好：不干扰其他 filter、不需要"记得恢复"、也不依赖某个可能再次被删的常量。

### 27.4 审计结果：发现 6 项问题，其中 1 项高危

完整报告见 `docs/审计报告-2026-10-27-第18轮.md`。摘要：

## 28. 2026-10-27 · M2b 第一小步：内核验 SHA-256 校验和（R1 已解决）

### 28.1 上一轮遗留的 R1 是什么

M2a 只校验魔数与版本。若 ADS 里的 `file_id` 被改而魔数保持不变，M2b 会用错误的 tweak 解密：
**得到乱码 → 应用若把乱码回写 → 文件损坏且不可逆。**

这是会导致用户数据丢失的风险，必须在 M2b 正式加解密之前堵掉。

### 28.2 本轮做法

内核用 BCrypt 算 `SHA-256(bytes[0..24])`，与元数据里的前 8 字节校验和比对。三种结果分开计数：

| 情形 | 计数 | 含义 |
|---|---|---|
| 魔数/版本/长度不对 | `AdsBroken` | 不是我们的标记，或格式坏了 |
| **魔数对但校验和不符** | **`AdsTampered`** | **是我们的标记，但内容被改过 —— 安全事件** |
| 全部通过 | `AdsHit` | 可用于 M2b 加解密 |

`AdsTampered` 单独列出来的价值：运维能一眼分辨"这里有别的程序的 ADS"和"有人在改我们的标记"。

### 28.3 两个必须记住的技术事实

**① 内核不能用 `bcrypt.lib`，要用 `ksecdd.lib`**

第一次链接直接 `LNK1181: 无法打开输入文件 bcrypt.lib`。原因：`bcrypt.lib` 在
`Windows Kits\10\Lib\<ver>\um\x64\`（**用户态**导入库）；内核里的 BCrypt 由
`ksecdd.sys`（Kernel Security Support Provider）提供，导入库在 `Lib\<ver>\km\x64\ksecdd.lib`。

**② 算法两端必须交叉验证，否则全线瘫痪**

内核用 BCrypt、用户态用 Rust `sha2`。两者只要有一处不同（实现、字节序、偏移），
**所有合法标记都会被判成篡改**，M2b 直接不可用。

实测：

| 实现 | 校验和（前 8 字节） |
|---|---|
| Rust `sha2` | `6463c5099f757a10` |
| **CNG / BCrypt**（.NET `SHA256` 走的就是它） | `6463c5099f757a10` |

完全一致。并把整个 32 字节样本锁死为黄金样本：

```
4f474d3101010000112233445566778808070605040302016463c5099f757a10
```

谁改了哈希算法、字段偏移或字段长度，`meta::tests::golden_meta_bytes` 立刻失败。

### 28.4 安全默认：验不了就不加载

`DriverEntry` 里 `BCryptOpenAlgorithmProvider` 失败 → **直接返回错误，驱动拒绝加载**。

理由：验不了校验和就守不住 R1。宁可整个驱动起不来（可诊断、可排查），
也不要静默降级运行（会毁数据且没人知道）。

### 28.5 为什么本轮**没有**改用 HMAC

裸 SHA-256 有一个已知缺口：攻击者若有写权限，可以改 `file_id` 再**重算校验和**，从而绕过检查。

改用 `HMAC-SHA256(设备密钥, ...)` 能防住，但会引入一个**更严重的可靠性风险**：
设备密钥一旦丢失，**所有文件的标记都无法验证 → 全部文件不可解密**。
对一个主打"驱动坏了还能救"的产品，这把钥匙不能轻率加进来。

**首选缓解是侧表**（原来就在 M2 计划里的 `Data/DriverIndex.db`）：独立记一份 路径 → file_id，
ADS 被改坏时能对照恢复。不引入新密钥，且顺带解决"ADS 在 U 盘/备份里丢失"的问题。

这条已作为 **A1（中危）** 记入第 19 轮审计报告的遗留清单。

### 28.6 验证方式（重启后会自动执行）

`driver\verify.ps1` 新增 **6b 篡改检测**：

1. 用 Win32 `CreateFileW/WriteFile` 写入一份**伪造的 32 字节标记**
   （魔数/版本合法、`file_id` 是假的、校验和全 0）；
2. 断言 `AdsTampered ≥ 1`（驱动认出了篡改）；
3. 断言 `AdsHit = 0`（驱动**没有**采信伪造的 file_id）。

**顺带一个坑**：写二进制 ADS 只有 Win32 API 可行——
`.NET` 的文件 API 不支持 `file:stream` 路径；`cmd` 的 `copy /b src dst:stream` 报
"文件名、目录名或卷标语法不正确"；`type src > dst:stream` 是文本模式会破坏字节。
所以脚本里内嵌了 `Add-Type` P/Invoke（`OugAdsWriter`），本次已实测写入成功。

用户态一侧也验了同样的逻辑：伪造标记后 `rescue info` 报
