## 1. 2026-10-26 · 项目立项与接续基建装备

**用户原话**：

> 「我想做一个企业内部文件防泄露的应用，分两端，一端是Server端，主要是权限控制，一端是Client端，安装后不允许被关闭或者卸载。且安装了Client端的电脑加密规则随服务端，只要有修改的就会自动加密，收到方会打不开且文档中有相应的公司防泄密信息等。但有安装过CLient的可以直接解密打开，关于哪些格式的文件要加密或者不加密能通过Server的规则来判断。可以多个人共用某一个加密规则等等，这是我的一个大概的需求，你要帮我完善，且要先参考全局用户指令完成这块的功能再继续」

### 1.2 需求完善（详见 `docs/需求说明书.md`）

- 把口述需求拆为 12 项服务端 + 14 项客户端功能需求（FR-S-* / FR-C-*）、9 项非功能指标、7 条验收标准、M1/M2/M3 分期。
- 明确"加密哪些格式"的判定口径：**服务端规则集（扩展名/文件名/路径/进程/大小）+ 优先级 + 默认动作**，客户端只执行；规则集与终端组多对多（满足"多人共用规则"）。
- 明确"未装客户端打不开 + 有公司防泄密信息"的实现：容器明文头（公司信息/提示语/密级/创建者）+ 密文主体。

### 1.3 架构取舍（详见 `docs/架构设计.md`）

| 决策 | 理由 | 备选（未采用） |
|---|---|---|
| M1 采用**用户态容器 + 受控打开** | 可交付、跨平台、无驱动签名风险 | 内核 minifilter（需 C++/WDK + EV 签名，工期与蓝屏风险高一个量级） |
| 容器格式自研（`OGD1` + AES-256-GCM 分块 + 明文头 + KeyBlock） | 需要"未装客户端可见提示"，标准加密格式做不到 | ZIP+AES、7z 容器（无自定义明文头、不可控） |
| 双端共享 `core` crate | 规则判定与容器格式必须字节级一致 | 两端各写一份（必然漂移） |
| 密钥体系 MasterKey → PolicyKey(HKDF) → DEK | 规则集可独立轮换，旧文件仍可解 | 单一全局密钥（轮换即导致历史文件不可读） |
| 文件监控新增 `notify` 依赖 | dhrust 无文件系统事件能力；纯 Rust 可交叉编译 | 自写 ReadDirectoryChangesW（Windows 专用，Linux 需再写 inotify） |

### 1.4 安全边界（已写入需求文档，需向客户如实传达）

- 用户态方案**不对抗**本地管理员 + 内核工具 / PE 修改 / 重装系统；目标是防普通员工误传与外带，不是防恶意管理员。
- 不做进程注入、反杀软、键盘记录、远程截屏。
- "不允许关闭/卸载"以服务恢复策略 + 双进程互保 + 服务 ACL + 服务端卸载令牌实现，属合规管控。
