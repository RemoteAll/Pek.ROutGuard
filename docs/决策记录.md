## 2. 2026-10-26 · 系统文件零影响（硬保护）+ Windows 全版本兼容

**用户原话**：

> 「这个有一点要考虑的就是不要影响到系统本身的文件，我们主要是使用windows系统，但可能windows的各个版本以及服务器版本都有可能会使用」

### 2.1 落地（代码）

- `core::rules` 改为**三级判定**：硬保护（`builtin:system`，**任何规则不可覆盖**）→ 软排除（`builtin:default-exclude`，**规则之前**放行）→ 规则集排除 → 规则（优先级降序）→ 默认动作。
- 硬保护覆盖：`\Windows\`、`\WINNT\`（老系统）、`\Program Files\`、`\Program Files (x86)\`、`\$Recycle.Bin\`、`\System Volume Information\`、`\Config.Msi\`、`\Documents and Settings\`；盘符根 `X:\boot|efi|recovery|perflogs|$WinREAgent`；系统文件 `pagefile.sys`、`hiberfil.sys`、`swapfile.sys`、`dumpstack.log.tmp`、`ntuser.dat`、`ntuser.ini`、`bootmgr`、`bootnxt`。
- **不绑定 `C:`**（Windows 可装 D 盘）；**盘符根才生效**（`D:\Work\boot\` 不误伤）；UNC 共享盘不按盘符根处理。
- 软排除覆盖 Temp / AppData 缓存 / `.git` / `.svn` / `.hg` / `node_modules` / `__pycache__` / `.vs`；**ProgramData 有意不内置**（常放业务数据，由显式规则决定）。
- 公开 `is_hard_protected` / `is_soft_excluded` / `system_protection`，供服务端校验 `watch_roots` 与面板提示。

### 2.2 对两个决策的影响（强化结论）

- **加密层级**：更坚定选 **A 级用户态**。B 级（minifilter）工作在文件系统层，与系统更新/杀软/文件系统行为的耦合正是"影响系统"的主要风险源（蓝屏最典型），且每个 Windows 版本都要单独验证内核行为；A 级只依赖稳定的用户态 API，天然满足"不影响系统"。
- **算法**：更坚定选 **AES-256-GCM**。AES-NI 让加密的 CPU 开销可忽略（服务器批量场景尤其重要）；SM4 只能软件实现，批量加密时明显占 CPU，与"不影响系统运行"冲突。

- `cargo test -p pek-outguard-core`：**43 passed / 0 failed**（新增 7 项系统保护区用例，含"故意配 `C:\Windows` 加密规则仍不加密"的反证）

**用户原话**：

> 「那如果要申请解密并分享出去的这种场景有考虑到么？」

**此前状态**：只有需求预留（`FR-S-08`、`Og_Approval` 表、`/api/client/approval` 接口），没有设计细节。

**本轮补齐**（新文档 `docs/外发审批与外发包设计.md`）：

- 把"分享"拆成四条路径：**内部同事（直传 `.ogd`，无需审批）** / 外部外发包 `.oge` / 完全解密（最高审批）/ 受控网页预览。
- **关键决策：外发包由客户端本机生成，服务端只签发授权令牌**——文件本体不出网、服务端不解密。
- 外发包 `OGE1`：OGD1 容器 + 明文头（接收方/有效期/次数/水印/令牌签名）+ **打开密码派生的 KEK 包裹 DEK**（PBKDF2-SHA256 60 万次）；包与密码分渠道发送。
- 查看器：单 exe 免安装；PDF/图片/文本内置预览不落盘；Office 转 PDF 后外发。
- 吊销：宽松（本地校验 + 联网回执）/ 强管控（每次打开联网校验）。
- **如实声明边界**：明文离开受控体系即不可控；查看器可被逆向，强约束必须靠联网校验；截图/拍照无法阻止，水印用于追溯与威慑。

**分期**：M1 继续"内部转发天然支持"，M2 做完整外发链路，不打乱 M1。

## 4. 2026-10-26 · Server 端形态：Tauri 桌面外壳（非服务本体）

**用户原话**：

> 「Server端可以考虑Tarui吧」

### 4.1 决策

- **采纳 Tauri**：作为**可选桌面管理端**（`admin/`，M2），加载与浏览器完全相同的一套面板。
- **服务本体仍是 HTTP 服务**：星尘托管、无头运行、多角色/远程访问；不把 Tauri 放进服务进程。
- **面板保持纯静态 + HTTP 优先**，不依赖 Tauri IPC —— 随时可退回浏览器。
- **单机版**（Tauri + sidecar + SQLite）作为 M3 可选发行形态，面向无需独立服务器的小客户。

### 4.2 理由

1. 服务器常驻且无人登录时 Tauri 窗口无法渲染，与星尘托管/服务化冲突；
2. 审批人、审计员需要浏览器/手机访问，桌面外壳会挡路；
3. 服务与 UI 同进程会放大故障域（UI 崩溃 = 服务不可用、升级必须带 UI）；
4. 但桌面外壳确实解决"输地址麻烦、无通知、无托盘"，且**零重复开发**（同一份 `server/res` 面板）。

### 4.3 依赖提醒

- WebView2：Win10 1803+/Win11 自带；**Server 2016/2019 需预装 Evergreen Runtime**（安装包内置 bootstrapper）。
- Tauri 2 构建期需 Node.js；产物 `.msi`/`.exe` 约 5–10 MB。
- 单机版 sidecar：`pek-outguard-server.exe` 作为 externalBin。

### 4.4 验证

- 本轮仅架构定稿（`docs/架构设计.md` 第 13 章），**未引入 Tauri 工程**（避免未验证的构建链进入仓库）。

## 6. 2026-10-26 · 人员与设备管理 + 外发形态澄清

**用户原话**：

> 「Server端要有人员管理功能，Client要把每台电脑的一些基础数据能当惟一码的到Server做存储处理，Server端会配置每一个Client的用户名和权限，以及相应的部门等管理。外发包没有密码吧，这个是解密之后就可以直接发出去的吧」

### 6.1 人员与设备管理（设计 + 代码）

- **服务端新增**（FR-S-13/14/15）：人员档案（姓名/工号/部门/职位/联系方式/状态/角色）、部门树（含负责人）、**终端 ↔ 人员多对多绑定**（支持多人共用一台电脑）、终端策略组与功能权限（是否允许申请解密/外发/离线）。
- **三种身份分开**：面板登录用户（管理员/审批人/审计员，走 Pek.RAdmin 用户与权限）、**员工档案**（`Og_Staff`，无密码，按终端上报的 Windows 用户名匹配）、**终端**（`Og_Client`，机器码为唯一码）。
- **设备唯一码落地**（FR-C-19）：`core::machine::machine_id(SMBIOS UUID, MachineGuid, 卷序列号)` → SHA-256 前 128 位；格式差异归一化（大小写/大括号/连字符）；三者全空报错；只采到一项也能生成；不加安装随机盐（否则重装后认不出同一台机器）。虚拟机克隆会撞码 → 面板提示人工绑定。
- **协议扩展**：`RegisterRequest` 增加 `hardware`（CPU/内存/磁盘/构建号/域）、`loggedUser`、`ip`、`mac`、`installedAt`；旧客户端 JSON 仍可解析（向后兼容测试）；心跳新增 `ip/mac/hardware` 变化项（未变化不发）。
- **数据表**：`Og_Department`、`Og_Staff`、`Og_StaffClient`；`Og_Client` 扩展为一台电脑的完整资产台账。

### 6.2 外发形态澄清（重要）

**用户理解校正**：外发包 **≠** 解密后的文件。

| 形态 | 对方需要什么 | 密码 | 失控风险 |
|---|---|---|---|
| **完全解密（主路径）** | 无（就是原始 docx/pdf） | 无 | 高（可任意转发） |
| **外发包 `.oge`（可选）** | OutGuard 查看器（免安装 exe） | **默认无**，可设 | 低–中（靠有效期/次数/水印/回执） |

- 按用户口径调整：**"审批通过 → 解密 → 直接发"列为最常用路径**（不走查看器、不设密码）。
- 外发包的**密码改为可选项**（需要防转发时才设，且与包分渠道发送）。
- 需求与外发设计文档已同步：完全解密列"最常用"，外发包默认无密码。

## 7. 2026-10-26 · 外发包密码策略（三档）

**用户原话**：

> 「外发包需要弄解密密码嘛？还是说什么样的？」

### 7.1 结论（已写入外发设计 5.1/5.2）

| 档位 | 密码 | 适用 | 保护强度 |
|---|---|---|---|
| **无密码（默认）** | 不需要 | 普通商务往来、"让对方看一眼" | 格式保护 + 行为管控（有效期/次数/水印/回执） |
| **随机密码（敏感件推荐）** | 系统生成 8–12 位，审批人可见 | 合同、图纸、报价 | PBKDF2-SHA256 60 万次 + AES-256-GCM |
| **固定密码** | 审批人设定 | 与固定客户的长期约定 | 同上（密码复用有风险） |
| （可选）绑定接收方 | 手机号后 4 位 / 工号 | 免传递场景 | 弱口令 |

- **密码必须与包分渠道发送**（包走邮件/IM，密码走电话/短信），否则等于没设。
- **技术真相**：无密码外发包的 DEK 用查看器内置固定 KEK 包裹 → 只做格式保护，**逆向可破**；有密码才是密码学保护。此结论已如实写入文档（安全边界第 5 条）。
- 三档建议：普通商务 → 无密码；敏感件 → 随机密码；必须可控 → 受控网页预览（不落盘）。

## 11. 2026-10-27 · 离线可用（断网照常保护，联网自动补同步）

**用户原话**：

> 「有一点要留意，如果网络不通的情况下，Client 要用本地已同步的规则，当连接上后再定时同步 Server 的」

### 11.1 设计口径

| 场景 | 行为 |
|---|---|
| 断网时保存受控文件 | **照常自动加密**（用 `Data/state.json` 缓存的规则集与密钥） |
| 断网时产生的审计 | 进本地队列（上限 5000 条），联网后按 200 条/批补传 |
| 断网时启动客户端 | **不退出**，用缓存策略启动监控（没有缓存则告警空转，联网后自动启用） |
| 首次安装就断网 | 不崩溃；每 60 s 重试注册，联网后自动补齐身份+策略+监控 |
| 恢复联网 | 心跳探测到后自动补同步（版本比对）+ 补传事件 + 重建监控（只在根变化时） |
| 长期离线（拔网线绕过） | 超过服务端 `OfflineGraceDays` 后**拒绝解密/受控打开**，但**自动加密继续**（用户数据不丢） |

### 11.2 落地

- 协议：`PolicyBundle.offline_grace_days`（服务端 `OfflineGraceDays`，默认 7 天；`0` = 不限制）。
- 状态：`ClientState.last_online`（离线判定基准）+ `offline_reported`（离线告警去重）+ `offline_secs/offline_days/offline_grace_days/offline_exceeded/offline_block_reason`。
- 运行时：`prepare_online`（非致命）、`mark_online`（在线状态变化记一条日志）、`retry_register_if_needed`（断网安装补注册）、`reconcile_watch`（监控根与策略每轮对齐）、`check_offline`（超期告警一次）。
- 解密闸门：`ops::decrypt_file` 开头校验离线宽限；`open_file` 走同一路径，自动加密不受影响。
- `status` 展示：`连接：`（在线 / 最近通信 N 分钟前 / 离线约 N 天）+ `离线宽限：7 天（剩余 N 天）`。

## 12. 2026-10-27 · 受控打开闭环 + 文件关联 + 安全阀（不碰正式文件）

**用户原话**：

> 「这里有个问题吧，安装了 Client 的通过其他软件不能直接打开吗？岂不是每次都要先解密才能打开？」
>
> 「需要无感」
>
> 「而且目前调试阶段不要影响到我正常的使用，也就是在没有完整确认无误不要加密我正式的文件」

### 12.1 先把概念说清（受控打开 ≠ 申请解密）

| 动作 | 需要审批 | 能干什么 |
|---|---|---|
| **受控打开**（双击 `.ogd`） | 不需要 | 解密到受控临时目录交给 Office；保存**自动回写成密文**；离线宽限期内照常用 |
| **申请解密 / 申请外发** | 需要（联网） | 拿到**干净明文**（外发给没装客户端的人 / 永久明文存档），高危，必须审批 |

所以「实际都是加密文件在用」是设计目标，但**不影响日常办公**——前提是受控打开闭环必须做对。

### 12.2 修掉的致命缺陷：编辑后改动丢失

原实现 `open` 只是“解密到临时目录 → 交给 Office”，用户改完保存：
改动只落在临时明文上，**密文里还是旧内容**（用户白干），且明文永久残留。

现在的闭环（`client/src/opensession.rs`）：

1. 打开时解密为 `{临时目录}/{原名}.{会话ID}.{扩展名}`，会话登记到 `Data/sessions.json`（**绝对路径**）；
2. 常驻服务监听临时目录，改动去抖 3 s 后用**原容器同一把策略密钥**重新加密，原子替换回 `.ogd`（保留原密级/创建者/规则）；
3. **内容哈希去重**：打开文件本身也会触发 Modify（访问时间/锁文件），内容没变不重复加密；
4. 会话超时（2 小时且近 10 分钟无改动）才清理明文——不删正在编辑的文件。

实测（真实文件）：

```
受控打开：...\季度报告.pdf.ogd → ...\季度报告.a13c00f1.pdf（会话 a13c00f1）
受控打开回写完成：... 第一季度 v1（37 字节）
受控打开回写完成：... 第二版 v2（75 字节）      ← 用户在 Office 里改的
解密验证：内容 = “季度报告 第二版 编辑后内容 v2 - 用户在 Office 里改的”
```

### 12.4 安全阀（用户硬要求：调试期不碰正式文件）

| 阀 | 默认 | 效果 |
|---|---|---|
| **`Mode = "dry_run"`** | ✅ 开启 | 只按规则判定并记日志，**不加密/不移动/不删除任何文件** |
| **`AllowRiskyRoots = false`** | ✅ 开启 | 桌面/文档/下载/用户目录本身/盘符根/系统目录 → **自动跳过并告警** |

## 16. 2026-10-27 · 密文写入时机（打开不该重写密文）

**用户原话**：

> 「这个密文应该不会经常变吧？」

### 16.1 实测发现的真问题

原去重只靠**内存表**（`Inner.sealed`），服务重启即失效。实测：

```
读取前：2026年度合同.txt.ogd  628 字节  13:55:53
读 10 次 + 列目录 10 次
读取后：2026年度合同.txt.ogd  628 字节  13:56:03   ← 时间戳变了！
```

原因：ProjFS 的 **hydrate**（用户打开文件时把内容填充到本地缓存）也会产生 `Modify` 事件，
服务重启后内存去重表为空 → 判定"内容变了" → **整文件重新加密**。
后果：① 用户只是"看了一眼"就产生写放大；② 备份/同步工具每次都认为文件变了要重传；③ SSD 额外磨损。

### 16.2 修法：以密文库容器头为准

容器头里本来就记了 `plainSha256`。去重改成：

```
内存表命中 → 用内存哈希（快路径）
内存表未命中 → 读密文库容器头的 plainSha256 比对（准，重启后依然有效）
```

内容一致就**只降级占位符**（必须做，否则磁盘留明文），不写密文库、不记审计。

### 16.3 修复后实测

```
读取前：628 字节  13:56:30
读 10 次 + 列目录 10 次
读取后：628 字节  13:56:30   ← 一个字节都没变

修改内容（Ctrl+S）→ 622 字节  13:56:46   ← 只有内容真变才写
再连读 5 次       → 622 字节  13:56:46   ← 仍然不变
```

### 16.4 写入时机的完整口径（交付文档要写）

| 操作 | 是否改动密文 |
|---|---|
| 打开 / 浏览 / 搜索 / 复制 / 列目录 | ❌ **完全不变** |
| 保存（内容真的变了） | ✅ 写一次 |
| 导入新文件 | ✅ 写一次 |
| 服务重启 | ❌ 不写（不再因内存表清空而重加密） |

**仍需注意**：每次保存是**全文件重加密**（OGD1 格式的分块 AAD 绑定头部哈希，不支持局部重写）。
所以大文件（几百 MB 的 CAD）每次 Ctrl+S 都会全量读写一遍。后续可做分块增量格式（需 V2 容器）。

### 16.5 部署建议（减少无谓 IO）

- `Data\Vault` **不要**放在云同步盘（OneDrive/坚果云）里，否则每次保存都会触发上传；
- 杀毒软件建议把 `Data\Vault` 加入**实时扫描排除**（密文扫描无意义，只增 IO）；
- 备份走定时快照（下一轮做 `vault backup`），不要用"逐文件实时同步"。

## 17. 2026-10-27 · 性能与安全收口（大文件不吃内存 · 磁盘不留明文 · 保存不全盘扫描）

> 用户原话（本轮要求）：
> 「请继续，这个一定要让用户无感知，且不会影响实际使用性能，也不会让操作变复杂，而且绝对要安全」
> 上一轮追问：「这个密文应该不会经常变吧？」（已由第 16 节回答并验证）

### 17.1 本轮揪出的 6 个真问题

| # | 问题 | 后果 |
|---|---|---|
| P1 | 打开文件时 `plain()` 把**整个文件读进内存** | 500 MB 图纸峰值近 1 GB，进程可能被 OOM 杀掉 → 服务挂 |
| P2 | 中间版本改成"解密到磁盘缓存 `VaultCache/*.plain`" | **明文落在磁盘上**——对 DLP 产品是硬伤（比 OOM 更严重） |
| P3 | `seal_one()` 用 `std::fs::read` 读全文再哈希 | 保存大文件时同样吃满内存 |
| P4 | `seal_dirty()` 每次保存**全盘扫描**整个安全区 | 目录文件一多，保存就卡；与"资源与带宽"约定冲突 |
| P5 | 命令行 `secure-area run` 与后台服务**各写一份**保存监控 | 改一处漏一处（CLI 那份还在全盘扫描） |
| P6 | 落位密文用裸 `std::fs::rename` | 杀软/备份恰好占着目标文件时"拒绝访问"直接失败，明文留到下次 |

**还有一个更隐蔽的**：

| # | 问题 | 后果 |
|---|---|---|
| P7 | 读完之后 ProjFS 把**明文留在本地**，永远不收回 | 用户看一眼就关掉的文件，明文长期躺在磁盘上，DLP 形同虚设 |

### 17.2 改法（逐条对应）

- **P1/P2 → 按需区间解密**：新增 `core::container::decrypt_range(path, kek, offset, len, out)`，
  按分块直接定位（`data_start + index * (4 + chunk + 16)`），只解应用真正要看的那几块。
  **不写任何明文缓存**，内存占用等于一次回调的数据量。
  旧的 `VaultCache` 目录在启动时**一次性删除**（清理历史版本残留的明文）。
- **P3 → 全流式**：`core::crypto::sha256_file()` 256 KB 缓冲流式哈希；加密输入直接用文件句柄。
  保存 300 MB 文件，进程内存不变。
- **P4 → 精准路径**：新增 `seal_path(&Path)`，只处理监控到变化的那一个文件；
  `seal_dirty()` 降级为**启动兜底 + 手工清扫**。
- **P5 → 抽出公共件**：`runtime::attach_seal_watch(area, root)`，CLI 与服务共用同一份（含空闲脱水线程）。
- **P6 → 原子替换**：改用 `dhrust::io::safe_replace_file`（内部带占用重试）。
- **P7 → 空闲脱水**：记录"被读过哪些文件"（内存表），
  `dehydrate_idle(60s)` 把 60 秒没再被读的文件降级回占位符。
  **关键发现**：`PrjUpdateFileIfNeeded` 对"内容未变的完整文件"是 **no-op**，
  必须给它一个**不同的 ContentID**（`placeholder_for(..., seed)`）才会真正丢弃本地明文。
  不加这一条，日志说"已降级"但 `fsutil` 能看到 300 MB 明文原封不动躺在盘上。

### 17.3 两个避免"抖动"的细节（不然性能反而更差）

1. **水化（hydrate）不算"保存"**：打开文件也会产生 `Modify` 事件。
   若立刻降级，应用下一秒又要去召回 → 读 300 MB 变成反复水化/脱水。
   现在的口径：**内容与密文库一致时不立刻降级**，交给空闲脱水；**内容变了才加密并立即降级**。
2. **同一版本短时间内只算一次哈希**：`recent` 表按（大小 + mtime + 5 秒窗口）去重。
   否则读一次大文件会白算十几次 300 MB 的 SHA-256。

### 17.4 实测（release 构建，Windows 11）

**结论**：客户端自身只花 0.69 秒 CPU 就处理完 300 MB；
首次打开的 10 秒主要花在 Windows 把 300 MB 明文落到本地（ProjFS 机制决定，含杀软扫描），
再次打开走本地缓存是毫秒级。

### 17.5 必须如实写进文档的限制

- **文件正在被应用打开时，本地必然是明文**（ProjFS 机制），关掉 60 秒后自动收回；
- **保存仍是全文件重加密**（OGD1 分块 AAD 绑定头部哈希），超大文件每次 Ctrl+S 都要全量读写；
  要根治只有做 V2 分块增量容器（已列入下一轮候选）；
- 首次打开超大文件的耗时主要由操作系统落盘决定，客户端自身开销可忽略；
- 部署建议：`Data\Vault` 与安全区目录都加入杀软实时扫描排除（密文扫描无意义，明文扫描纯增 IO）。

## 18. 2026-10-27 · 结论性判断：ProjFS 做不到"打开期间不落明文"（附替代路线与许可证核实）

> 用户原话：
> 「如果打开时是明文，那这个方案就不可行了。」
> 「换其他开源方案？」

### 18.1 结论：ProjFS 这条路对 DLP 是死路

不是实现问题，是机制问题：**ProjFS 的 `PrjWriteFileData` 是把数据写进 NTFS 的水化缓存**——
只要应用用 `ReadFile` 读文件，Windows 就会把这段数据落成本地磁盘数据，这正是它读得快的原理。
没有任何启动选项能关掉这个行为（`PRJ_STARTVIRTUALIZING_OPTIONS` 只有负路径缓存之类的开关）。

我们能做的只是把窗口期从"永远"压到"空闲 60 秒"，**做不到零**。
对一个要防"内部人员用别的软件拷走明文"的 DLP 产品，这不够。

**因此：ProjFS 只能作为"过渡演示形态"，不能作为交付形态。** 第 17 节的性能优化与安全收尾全部保留有效
（容器/密钥/策略/审计/按需区间解密都是底层能力，换呈现层后继续用）。

### 18.2 替代路线（三选一，均已核实事实）

| | **Dokany（推荐）** | WinFsp | minifilter 自研驱动 |
|---|---|---|---|
| 形态 | 用户态文件系统，挂盘符/目录 | 同左 | 内核驱动，全盘透明 |
| 打开期间落明文 | ❌ **不落**（read 回调当场解密，数据只过内存） | ❌ 不落 | ❌ 不落 |
| 驱动签名 | **官方已签名**，装 msi 即可，**无需我们签名** | 官方已签名 | **需自备 EV 证书 + 微软 attestation 签名** |
| 许可证（关键） | **LGPL**（dokan2.dll / dokan2.sys / 安装器）+ MIT（dokanctl、样例）→ **闭源商业产品可用**（动态链接不传染） | GPLv3 + FLOSS 例外 + **商业许可另售**；Rust 绑定 `winfsp` crate 是 **GPL-3.0**（会传染） | 自有 |
| 支持系统 | Win7~11、Server 2008R2~2022，x86/x64/ARM/ARM64 | Win7+ | Win10+ |
| Rust 生态 | `dokan` crate = **MIT**，但版本停在 `0.3.1+dokan206`（2022-12）；Dokan 2.x C API 稳定，可自写薄 FFI 补 | `winfsp` crate 0.13.2（2026-10 活跃）但 GPL | 无（C/WDK） |
| 能拦"另存到桌面/临时文件" | ❌ 只能保证挂载盘内不落盘（靠 WatchRoots 兜底） | ❌ 同左 | ✅ **唯一真解** |
| 工作量 | 中（约一个模块 + 回调映射 + 调试） | 中 | 大（3~5 倍，蓝屏风险，需驱动测试机） |

**行业先例**：开源透明加密产品 **Cryptomator** 的 Windows 端就是"WinFsp 或 Dokan + 实时加解密 + 容器"这一套，
说明该架构可行且成熟。（它不选 GPL 绑定的方式，而是按需加载驱动 DLL。）

### 18.3 推荐

1. **呈现层换 Dokany**（LGPL，不用买许可、不用签驱动）。
2. **Dokan 只保证"安全区里的文件不落明文"**；"另存到桌面"仍靠 `WatchRoots` 再加密兜底——
   这一点必须写进交付文档，不能让客户以为全拦。
3. **要连"另存到别处"一起拦**，只有 minifilter；那是第二阶段（需 EV 证书），不是现在能做的。
4. 复用清单：容器 OGD1、密钥体系、策略下发、审计、`container::decrypt_range`（正好就是 Dokan read 回调要的）
   **全部复用**；报废的只有 `secure_area.rs` 这一个模块（ProjFS 回调层）。

### 18.4 本轮顺带修掉的两个真实漏洞（与呈现层无关，换 Dokan 前也必须修）

**漏洞 1：服务被强杀/升级后，安全区永久起不来**

实测复现：强杀进程后目录里留下 ProjFS 占位符（属性 4204064 与 9760 两种形态），
而 `check_area`/`start` 要求"目录必须为空"→ **一次崩溃就让安全区再也启动不了**，用户看到的是文件全没了。

修法：
- `is_placeholder()` 补上第二种形态（`ReparsePoint + Sparse`；provider 停止后 ProjFS 会撤掉 `RECALL_ON_DATA_ACCESS`）；
- `check_area()` 只拒绝**真正的明文实体文件**，允许残留自家占位符；
- `start()` 删除重复的"必须为空"检查，改为复用 `check_area()`（两套口径打架正是根因）；
- `absorb_existing()` 跳过占位符（provider 未启动时读它没有意义，还会搞乱 ProjFS 的脏状态）。

实测：强杀后 `secure-area status` 报"可直接启用"，重启后 `采购合同.docx`(5,242,880 B)、
`big.bin`(314,572,800 B) 都能正常读出，**数据未丢**。

**漏洞 2：服务正常停止时明文留在磁盘上**

`Drop` 里原来是"先 `PrjStopVirtualizing` 再释放"——ProjFS 一停，已水化的文件就退化成实体文件，
明文留在盘上（升级、重启时最容易漏）。修法：`Drop` **先** `dehydrate_idle(0)` + `seal_dirty()` 收回明文，
再停止虚拟化。
