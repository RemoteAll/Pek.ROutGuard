## 2. 安全审计

### 2.1 S1（**高危**，已修复）控制设备没有安全描述符 → 任何本地用户都能关掉加密

**问题**
`OugCreateControlDevice` 用 `IoCreateDevice` 创建 `\Device\PekOutGuardFilter`，**未指定任何 DACL**。`IoCreateDevice` 的设备对象默认安全描述符允许 `Everyone` 访问。

**后果（对 DLP 是致命的）**
任何普通域用户/本地用户都可以：

| 操作 | 命令 | 后果 |
|---|---|---|
| 清空规则 | `driver rules --clear` | **整个受控目录瞬间变成不加密** |
| 关闭判定 | `driver disable` | 同上 |
| 读统计 | `driver status` | 泄露最近命中的**完整文件路径**（`\Device\HarddiskVolume3\研发部\并购方案.docx`）——这本身就是情报泄露 |

也就是说：**防泄漏产品自己被被防的人一键关掉**。

**修复**
改用 `IoCreateDeviceSecure` + SDDL：

```
D:P(A;;GA;;;SY)(A;;GA;;;BA)
 │  │       │      └─ BA = Builtin\Administrators 完全访问
 │  │       └──────── SY = LocalSystem 完全访问
 │  └──────────────── GA = GENERIC_ALL
 └─────────────────── D:P = DACL 受保护（不继承父对象宽松权限）
```

其余身份（含普通用户、`Users`、`Authenticated Users`）一律无权打开设备。

**配套**：`wdmsec.lib` + `BufferOverflowK.lib`（后者提供 `__security_cookie`，`wdmsec.lib` 依赖它）。

**验证方式**（重启后必做）
```powershell
# 管理员：应成功
.\target\debug\pek-outguard-client.exe driver status

# 普通用户（非提权 PowerShell）：应失败，且错误是"拒绝访问"
.\target\debug\pek-outguard-client.exe driver status
```

**部署约束（必须写进部署文档）**：客户端服务进程必须以 **LocalSystem** 运行，否则它自己也读不到驱动设备 → 表现为"策略下发失败"。

### 2.2 S2（**中危**，已修复）规则字符串"强制截断"可导致误判受控

**问题**
M1 的 `SET_RULES` 处理只把每个字符串的**最后一个字节**置为 NUL：

```c
g_Rules.PathPrefixes[i][OUG_MAX_PATH - 1] = L'\0';   // 旧代码
```

如果调用方传入 260 个非 NUL 字符，这等于**悄悄把规则截短成 259 字符**。截短后的前缀匹配范围变大，可能把不该加密的目录判成受控——或者反过来。

**修复**
逐个字符串扫描，必须在有效范围内找到 NUL，否则**整包拒绝**（`STATUS_INVALID_PARAMETER`）。拒绝比"猜"安全：宁可这次规则下发失败、沿用旧规则，也不要带着一条含义不确定的规则去加密用户文件。

---

### 2.3 S3（**中危**，M1 遗留，已修复）超长路径"截断后参与匹配"

**问题**
`OugPreCreate` 里取到规范化路径后：

```c
if (copyChars >= OUG_MAX_PATH) { copyChars = OUG_MAX_PATH - 1; }   // 旧代码
RtlCopyMemory(pathBuf, ...); pathBuf[copyChars] = L'\0';
matched = OugRulesMatchLocked(pathBuf);      // ← 拿截断的路径去匹配
```

路径被截断后，末段（扩展名）就丢失了 → 一个 `D:\机密\...（超长）...\方案.docx` 会被当成 `...\方案.d`，扩展名规则全失效；反过来，截断后恰好在某个前缀规则覆盖范围内时会被误判为受控。

**修复**
超长路径**直接判"不命中"**并记 `RuleEvalError`，绝不拿截断值参与任何判定。口径与"规则未下发时一律不命中"一致：**存疑时选择不加密**（不加密最多是保护不足，错误加密可能导致文件打不开）。

---

### 2.4 S4（**中危**，功能缺陷，已修复）`RESET_STATS` 漏清 M2a 字段

**问题**
统计清零只清到 M1 的 `RuleEvalError`，M2a 新增的 `AdsHit/AdsAbsent/AdsBroken/AdsError` 没清。
后果不是安全问题，但会让"清零"看起来没生效 → **验证脚本在 reset 后读到旧计数而误判**（把上一个文件的探测结果当成这个文件的）。这类"看起来像 bug 的假信号"在事故排查时会极大干扰判断，所以按中危处理。

**修复**：五项一起清零，`LastAdsFileId` 一并零化。

---

### 2.5 S5（**性能/稳定性**，已修复）规则匹配在自旋锁内做长循环

**问题**
M1 在 `DISPATCH_LEVEL` 自旋锁里做最多 48 条规则 × 最长 260 字符的比较，外加 520 字节的 `LastHit` 拷贝。最坏情况几百微秒——期间**其他所有 CPU 都在自旋等待**。这对一台跑 CAD 的工作站是实打实的系统级卡顿源。

**修复**
改为**双缓冲无锁读**：

- 两块静态 `OUG_RULES` + 一个 `volatile LONG` 索引；
- 写（IOCTL，极罕见）：填非当前块 → `InterlockedExchange` 切换索引（x86 上带全屏障）；
- 读（PreCreate，极热）：一次原子读拿索引，无锁遍历。

切换瞬间可能有单个 I/O 用到上一版规则——与"规则滚动更新"语义一致。旧缓冲是静态内存、永不释放，不存在 use-after-free。

**收益**：回调内**零自旋锁**。

---

### 2.6 S6（**可观测性**，已修复）正常情形被记成错误

**问题**
PreCreate 偶发在 `APC_LEVEL`（分页 I/O），此时不能发起 `FltCreateFile`/`ZwReadFile`。原实现把它记进 `AdsError`。内存压力大时 `AdsError` 会飙升，运维会去查一个根本不存在的故障。

**修复**：新增 `AdsSkipped`，语义为"这次没做探测（不是错误）"。`AdsError` 只留真正的问题（权限异常、文件被删等）。

### 2.7 已核查、确认无问题的项

| # | 检查项 | 结论 |
|---|---|---|
| 1 | **递归/重入** | `FltCreateFileEx2` 传 `FltObjects->Instance`，I/O 从**本实例下方**发起，不会再进入自己的 `PreCreate`。另外 `Instance == NULL` 时直接放弃探测。原先用 `IoSetTopLevelIrp(FLT_TOP_LEVEL_IRP)` 的方案已废弃（WDK 26100 移除该常量），现方案更干净且不干扰其他 filter |
| 2 | **资源泄漏** | `handle` / `fileObject` 在成功、失败、短读三条路径上都已释放；失败路径额外处理了"`FltCreateFileEx2` 失败但仍返回文件对象"的情形 |
| 3 | **缓冲区边界** | `streamPath` 266 个 WCHAR；`PathChars` 实测上限 259（≥260 已被 S3 的修复拦掉），`PathChars + 4 + 1 ≤ 264 < 266` 恒成立 |
| 4 | **IRQL** | `FltCreateFileEx2` / `ZwReadFile` 都在 `KeGetCurrentIrql() == PASSIVE_LEVEL` 检查之后；栈上 32 字节缓冲在 PASSIVE 下可作为 I/O 缓冲 |
| 5 | **未初始化内存** | `meta` 先 `RtlZeroMemory` 再读；`ioStatus` 由 API 填写 |
| 6 | **死锁** | ADS 探测在 `FltReleaseFileNameInformation` 之后、且不持有任何锁时发起 |
| 7 | **句柄不泄露到用户态** | `OBJ_KERNEL_HANDLE` |
| 8 | **只读保证** | 只请求 `FILE_READ_DATA`，`FILE_OPEN`（不创建、不覆盖），无任何写/删/改属性调用 |
| 9 | **内核不信任磁盘内容** | 魔数 + 版本 + 标志位三重校验；长度必须正好 32 字节 |
| 10 | **结构体协议漂移** | 两端 `C_ASSERT(sizeof(OUG_STATS) == 648)` / `assert_eq!(size_of::<DriverStats>(), 648)` 双向锁定 |
| 11 | **设备类型/打开方式** | `FILE_DEVICE_SECURE_OPEN`（防止通过符号链接绕过 DACL 做相对打开） |

## 3. 数据完整性审计

### 3.1 M2a 是否可能损坏文件

M2a 的动作只有两个：`FltCreateFileEx2(FILE_READ_DATA)` + `ZwReadFile(32 字节)`。**没有任何写路径**。因此结构上不可能损坏数据。

唯一需要担心的是**改变 I/O 结果**（比如让某个 Create 失败）——已通过"任何失败只计数、一律 `return FLT_PREOP_SUCCESS_NO_CALLBACK`"保证。

### 3.2 端到端回归（本轮实测）

```
明文 SHA256 = 176EFADB…  12617 字节
encrypt → 12617 字节（等长 ✓）内容已变 ✓
verify  → 12617 字节全部校验通过
decrypt → SHA256 与原文逐字节一致 ✓
```

XTS 批量化后，与 Windows CNG 的参考向量测试仍然通过（密文未变）。

## 4. 遗留风险（诚实列出，未解决的不写成已解决）

| # | 风险 | 等级 | 说明与计划 |
|---|---|---|---|
| R1 | **ADS 被篡改可导致用错 file_id** | **高（M2b 前必须解决）** | M2a 只校验魔数与版本，**没有校验 SHA-256 校验和**。若攻击者改掉 ADS 里的 `file_id` 而保持魔数/版本合法，M2b 会用错误的 tweak 解密 → 得到乱码 → 应用可能把乱码回写 → **数据损坏**。计划：M2b 在内核里用 `BCrypt` 算 SHA-256 校验（AES-ECB 已验证可用，SHA-256 同属 CNG 基础算法） |
| R2 | **`LastAdsFileId` 非原子（跨字段）** | 低 | 8 字节对齐写在 x64 上是原子的，但"最近一次"语义天然是多线程竞争的。该字段**只用于展示**，不参与任何加解密决策；M2b 必须从 per-file context 取 file_id，不得读全局统计 |
| R3 | **每个命中 Create 多一次 Create+Read+Close** | 中 | 未实测（驱动未加载）。Office 打开文档会发几十到上百次 Create，若开销明显，M2b 必须加 **stream handle 上下文缓存**（同一文件只探测一次）。`driver status` 的 `AdsHit/AdsAbsent` 可直接用来估量探测频次 |
| R4 | **驱动从未实际加载运行** | 高 | 全部内核结论来自静态审计 + 编译通过 + `C_ASSERT`。**必须**在重启后跑 `driver\verify.ps1` 才能确认 |
| R5 | **无 EV 代码签名** | 高（阻塞上线） | 自签名只能在 testsigning 模式加载。生产环境必须 EV 证书（¥3000~5000/年，采购 1~3 周）+ 微软 attestation |
| R6 | **普通用户无法访问控制设备（设计如此）** | 低 | 客户端服务必须以 LocalSystem 运行；需在部署文档中写明，否则表现为"策略下发失败" |

## 7. 可复用审计清单（以后每轮照此过）

### 7.1 安全

- [ ] **谁能改策略**：控制面入口是否有明确 DACL/鉴权？普通用户能否关闭防护？
- [ ] **不可信输入**：所有来自用户态/磁盘的字段，长度、计数、字符串结尾是否强制校验？（宁可整包拒绝，不要截断/猜测）
- [ ] **密钥与凭据**：是否有明文落盘？日志里是否打印了密钥？
- [ ] **失败时的默认方向**：出错时是"放行"还是"拦截"？本产品口径＝**存疑不加密**（见 S3）
- [ ] **信息泄露**：日志/统计/错误信息是否泄露文件路径、用户、密钥？
- [ ] **降级路径**：能否通过改名、复制到别的盘、卸载驱动绕过？绕过时有没有痕迹？

### 7.2 内核专项

- [ ] IRQL：每个可能阻塞的调用前是否检查 `PASSIVE_LEVEL`
- [ ] 递归：自发起 I/O 是否从本实例下方发起（或等价的防重入）
- [ ] 资源：每条 `return` 前 handle / file object / 名字信息都已释放
- [ ] 锁：回调里有没有自旋锁包住长循环；能否换成无锁/双缓冲
- [ ] 缓冲：偏移+长度的加法是否可能溢出；截断是否会影响判定
- [ ] 结构体协议：两端尺寸断言是否同步更新

### 7.3 数据完整性

- [ ] 本轮改动是否引入任何写路径？没有写路径就不会损坏数据（最强的保证）
- [ ] 加解密改动是否有**逐字节对拍**
- [ ] 是否有"出错也不影响原始 I/O"的硬保证（回调一律返回成功）

### 7.4 性能与资源

- [ ] 新增周期任务/回调开销是否算过账并记录
- [ ] 热路径是否零分配、零锁
- [ ] 有没有实测数据支撑（不是"应该很快"）

### 7.5 收尾

- [ ] 全量测试 + clippy 零告警
- [ ] 决策记录新增一节（含用户原话）
- [ ] 记忆同步 + 提交
- [ ] **遗留风险清单更新**（已解决的不再列，未解决的不许删）

## 8. 本轮审计结论

**发现并修复 6 项问题，其中高危 1 项（S1：任何人都能关掉加密）。**

S1 是本轮最有价值的发现——它不是本轮新引入的，而是从 M1 就存在、一直没被发现的缺陷。这说明**"每轮审计"这条制度本身就是有效的**：如果没有这次强制审计，这个缺陷会一直带到客户现场，等某个懂技术的员工用一行命令把整个公司的 DLP 关掉。

**当前不可上线的两个硬阻塞**：R4（驱动未实际加载验证）、R5（无 EV 签名）。这两项都依赖外部条件（重启 / 证书采购），不是代码问题。
