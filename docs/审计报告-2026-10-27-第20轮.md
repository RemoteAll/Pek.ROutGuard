## 1. 本轮范围与一个明确的边界

### 1.1 做了什么

| # | 内容 | 可验证性 |
|---|---|---|
| 1 | **用户态透明加密引擎** `client/src/transparent.rs`（13 项测试） | ✅ 完整验证 |
| 2 | **侧表** `client/src/index.rs`（8 项测试） | ✅ 完整验证 |
| 3 | **驱动密钥通道 M2c**（`SET_POLICY_KEY` IOCTL + AES 句柄 + 销毁） | ⚠ 编译验证，运行待重启 |
| 4 | **客户端服务接入驱动**：策略同步后自动推送规则与密钥 | ⚠ 运行待重启（失败不致命） |

### 1.2 明确**没有**做的一件事，以及为什么

**驱动层的实际加解密（Read/Write 变换）本轮没有做。**

理由不是"时间不够"，而是风险判断：

- 它需要处理：非对齐偏移、跨块、尾部、追加、截断、分页 I/O、缓存与直接 I/O 双路径、内存映射；
- 其中**任何一条写错都是用户数据损坏**，而驱动一旦加载，错误只会在蓝屏或文件打不开时暴露；
- 本轮**无法加载驱动验证**（testsigning 未开、不能重启）。

所以本轮先把这些边界条件在**用户态**全部实现并测试（第 1 项），让它成为内核实现的**黄金参照**。
下一轮等能验证时再搬进内核，并且可以拿同一批用例逐字节对拍。

这与产品口径一致：宁可慢一轮，也不能拿用户的真实文件做试验。

## 2. 安全审计

### 2.1 S1（**中危，已在本轮设计上规避**）驱动密钥的存放与生命周期

密钥是这套系统里最敏感的东西。本轮的处置：

| 环节 | 措施 |
|---|---|
| 传输 | 只经 `DeviceIoControl` 的 METHOD_BUFFERED 缓冲，**不落盘** |
| 日志 | `DbgPrint` 只打版本号，**绝不打印密钥**；Rust 侧 `KeyRequest` 的 `Debug` 实现显式输出 `<已隐藏>` |
| 驱动内存 | 存于驱动全局变量 + BCrypt 句柄；卸载时**先销毁句柄、再 `RtlSecureZeroMemory` 清原始缓冲** |
| 替换 | 先在新密钥上建好句柄，**全部成功后才切换**；旧句柄立即 `BCryptDestroyKey` |
| 下发权限 | 控制设备 SDDL 限定 SYSTEM/Administrators（第 18 轮 S1 修复） |

**核查过的点**：
- 若 `BCryptGenerateSymmetricKey` 第二个 key 失败，第一个会被销毁（无泄漏）；
- 若 `g_AesAlg == NULL`，`KeyState` 置 2 并返回 `STATUS_INTERNAL_ERROR`——**不会静默成功**让用户误以为密钥可用；
- `Version == 0` 的请求被拒绝（版本 0 保留为"未下发"语义）。

**遗留**：密钥在驱动内存中无法防物理内存读取/内核调试器（用户态 DLP 的固有边界，与所有同类产品一致）。已属于"不对抗本地管理员"的既有边界。

### 2.2 S2（**低危，已规避**）密钥派生的一致性

驱动拿到的 XTS 密钥来自 `crypto::derive_xts_key(policy_key)`，与用户态透明引擎使用**同一个函数**。
如果两边派生方式不同，透明加密后的文件用户态救援工具解不开。

**已核查**：`push_to_driver` 用的是 `ops::policy_key` + `crypto::derive_xts_key`，
与 `rescue_cipher`（救援工具）完全同一条链路 → 三者一致。

### 2.3 S3（**低危，已规避**）驱动接入失败不能影响主流程

`push_to_driver` 返回 `Result`，调用方：

```rust
match push_to_driver(state) {
    Ok(note) => dhrust::info!("{note}"),
    Err(e) => dhrust::debug!("驱动未接入（{e}）；用户态加密流程照常工作"),
}
```

**驱动没装/没加载是开发与灰度期的正常状态**，绝不能因为推不动规则就让策略同步失败——
那会导致终端离线误判、监控根丢失。已确认失败只记 debug 日志。

### 2.4 透明引擎的安全相关设计（新增代码重点审）

| # | 检查项 | 结论 |
|---|---|---|
| 1 | **磁盘上是否等于明文** | 有测试 `disk_content_is_ciphertext_not_plaintext`：断言磁盘字节 ≠ 明文，且密文中不出现明文片段 |
| 2 | **长度是否泄漏** | 磁盘长度 == 明文长度（等长的固有特性），这是透明加密必须付出的信息量；与 EFS/BitLocker 同级 |
| 3 | **同明文不同文件是否同密文** | 有测试 `different_file_ids_produce_different_ciphertext`：相同明文 + 不同 file_id → 密文不同 |
| 4 | **写入是否破坏相邻字节** | 有测试 `unaligned_write_preserves_surrounding_bytes`：非对齐、跨块写后全文比对 |
| 5 | **创建是否覆盖已有文件** | `create_new(true)`，有测试断言已存在时报错且原内容不变 |
| 6 | **截断后是否还能读** | 有测试覆盖块边界与非块边界两种截断，且**重开文件再读**验证已落盘 |
| 7 | **扩展区域是否是明文零泄漏** | 扩展写零后，该区域也按规则加密（不是裸零字节），有测试覆盖 |
| 8 | **零长文件** | 有测试：创建 0 字节、重开、len=0 |

### 2.5 侧表的安全相关设计

| # | 检查项 | 结论 |
|---|---|---|
| 1 | **是否会误判路径** | 统一分隔符 + 统一小写归一化；有测试覆盖大小写与正/反斜杠 |
| 2 | **索引损坏会不会拖垮主流程** | 坏行**跳过不报错**（索引是辅助证据，不能让它坏了就什么都读不出）；有测试 |
| 3 | **写入是否原子** | 临时文件 + `dhrust::io::safe_replace_file`（占用重试），断电不会写出半个索引 |
| 4 | **是否泄漏敏感信息** | 索引里只有 路径 + file_id + 时间，**没有密钥**；且 file_id 本身不足以解密（缺密钥） |
| 5 | **覆盖是否产生重复记录** | 有测试断言覆盖后条数仍为 1 |

## 3. 数据完整性审计

**本轮有没有引入写路径？** —— 分两部分回答：

| 部分 | 写路径 | 影响范围 |
|---|---|---|
| `transparent.rs` | **有**（这就是它的职责：写密文） | 只写它自己创建/打开的文件；有 13 项测试守着"读回等于写入" |
| `index.rs` | 有（写索引） | 只写 `DriverIndex/` 下的分片文件，不碰用户文件 |
| 驱动 M2c | **无** | 只存密钥句柄，不改任何数据 |
| 客户端推送 | 无（只发 IOCTL） | — |

**关键结论**：本轮唯一会碰用户文件内容的是 `transparent.rs`，而它**目前没有任何调用方**
（只作为参照实现和测试目标存在）。真正的加密仍走已验证的 `.ogd` 容器路径。
所以本轮改动对现网行为零影响。

端到端仍验证通过（上轮实测数据依然有效）：

```
明文 SHA256 = 176EFADB…  12617 字节 → encrypt → 12617 字节（等长）→ decrypt → 逐字节一致
```

## 7. 审计结论

**本轮验证了 21 项新测试，全部可复现。**

最有价值的不是"又加了几个功能"，而是把**驱动实现里最容易出人命的那部分逻辑先在用户态跑通并锁死**：
`truncate` 到非块边界这一条，如果没有 `truncate_to_non_block_boundary_keeps_plaintext_readable`
这个测试，内核实现几乎必定写错（直觉上"set_len 就行"），而症状是"用户把文件截短后文件永久打不开"。

**当前硬阻塞仍是两项外部条件**：R4（无法加载验证）、R5（无 EV 签名）。
**唯一已知的功能缺口**是 A3（驱动侧加解密），它现在有了完整的参照实现与测试用例，风险已大幅下降。
